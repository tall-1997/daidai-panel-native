## 版本概览

`v3.0.7` 是一个纯修复版，两个问题都来自用户反馈：

- **Docker**：容器设置 `PUID` / `PGID` 之后，面板里安装 Node.js / Python 依赖必报 `EACCES`，取消 `PUID` 就恢复。而 `PUID/PGID` 对 NAS（飞牛 / 群晖 / 绿联 / unRAID）是刚需。
- **Magisk**：Debian 版刷完之后 SSH 连不上，Alpine 版正常。

> ⚠️ **两项修复都需要重新部署才能拿到**：Docker 侧要重拉镜像，Magisk 侧要**重刷模块 ZIP**（面板内的一键升级只替换 `daidai-server` / `ddp` / `web`，覆盖不到模块外壳脚本）。

## 修复

### 容器设置 PUID/PGID 后，装依赖必报 EACCES

现象是这样的（用户原始报障）：

```
npm error code EACCES
npm error syscall mkdir
npm error path /home/daidai
npm error FetchError: Invalid response body while trying to fetch
  https://registry.npmmirror.com/got: EACCES: permission denied, mkdir '/home/daidai'
```

> **根因：降权只做了「换 uid」和「chown 数据目录」两件事，没有给这个新 uid 准备一个可写的家目录。**
>
> `entrypoint.sh` 建 daidai 用户用的是 `adduser -D -H`（Alpine）/ `useradd -M`（Debian），
> 这两个参数都是「**不创建家目录**」——但 `/etc/passwd` 里的家目录字段照写 `/home/daidai`。
> 而 `chown -R` 的白名单只有数据目录和 `/tmp`，`/home` 本身是镜像层的 `root:root 0755`，
> daidai 自己建不出这个子目录。
>
> npm 的 cache（`$HOME/.npm`）、`$HOME/.npmrc`，pip 的 `pip.conf` 与 `pip --user` 的落点，
> **全部只认 HOME**。于是「面板能开、一装依赖就 EACCES」。
>
> 顺带说明 npm 那句「Your cache folder contains root-owned files, please run sudo chown ...」
> 是个固定话术：真实情况多半不是「有 root 拥有的文件」，而是**那个目录根本建不出来**。
> 按它说的去 chown 是修不好的。

现在：

- 降权用户的 HOME 指向数据目录下的 `.home`（`/app/Dumb-Panel/.home`），启动时创建并 chown；
- 拉起面板时用 `/usr/bin/env` 把 HOME **显式钉一遍**——`su-exec` 会按 `/etc/passwd` 覆写 HOME，而 `gosu` 只在 HOME 为空时才设置（Docker 默认已经注入 `HOME=/root`），两个工具行为不一致，只靠 passwd 字段修不好 Debian 那条路。写绝对路径是必须的：`PATH` 首位是面板用户可写的 `deps/nodejs/node_modules/.bin`，裸写 `env` 会被一个同名的 npm bin 劫持掉；
- 代码侧加了一层对称兜底：安装依赖前探测 HOME 是否**真的可写**（不是「存不存在」，只读挂载 / 属主不符 / NFS root squash 都要真写一次才暴露），不可写就回落到同一个 `.home`，并同时钉住 `npm_config_cache`。这一层额外覆盖 Magisk 模块版与裸机 systemd 部署（`User=` 同样按 passwd 决定 HOME，家目录不存在时坏法一模一样）。
  依赖列表页与「导出依赖」也走同一份判定——`npm` 只要启动就会初始化 `$HOME/.npm` 的 cache，HOME 不可写时连 `npm list` 都跑不起来，那会变成「装得上、却看不到、也导不出」这种看起来毫不相关的两件事。
  > `HOME` **为空**时刻意**不**重定向：那时 npm / pip 会退回按 uid 解析家目录，而那个结果通常是对的（裸机 systemd 以 root 跑、没写 `Environment=HOME` 就是这种），改掉它反而会把用户手写在 `/root/.npmrc` 里的私有源与 token 静默弄失效。本次要修的场景里 HOME 一定是有值的。

顺带修好的三处，它们都在同一段代码里，而且比上面那条更致命：

- **`PUID=1000` / `PGID=1000` 在 Debian 镜像上会让容器直接起不来**。Debian 镜像基于 `node:20-bookworm-slim`，它**自带一个 uid/gid 都是 1000 的 `node` 用户**，而两份 compose 注释里给的示例恰好就是最常见的 `PUID=1000`。原来建组建用户的那几行在撞车时全部失败、末尾又没有兜底，`set -e` 会把整个入口脚本带出，用户看到的是「容器起不来」，零线索。现在 UID/GID 已被占用就直接**复用**那个现成的用户/组——降权真正需要的只是「进程的 uid/gid 对上」，账号叫什么无所谓。
- **复用现成账号时 `PGID` 会被静默丢掉**。`su-exec` 与 `gosu` 只给用户名的话，取的是 `/etc/passwd` 里那个账号的**主组**。群晖 / OMV 用户常见的 `PUID=1000 PGID=100(users)` 命中 `node` 账号后，数据目录被 chown 成 `1000:100`，面板进程却以 `gid=1000` 跑，新写出来的文件属组全错——而属组对得上正是设 `PGID` 的唯一目的。现在按 `user:group` 形式降权，`gid` 一律取 `PGID`。
- **改了 `PUID` 之后只做 `docker restart` 不生效**。容器可写层还在，上一次建的 daidai 用户会原样保留，于是 chown 出来的属主和进程实际的 uid 对不上。现在会用 `usermod` / `groupmod` 就地修正。

同时补上的细节：

- 只设 `PGID` 不设 `PUID` 时，`TARGET_UID` 会取到 0，原来会造出一个 **uid=0 的假 daidai**（看起来降了权、实际仍是 root）。现在直接跳过降权并打印说明。
- 启动预检除了数据目录，**单独再探一次 HOME**——「数据目录整体不可写、面板压根起不来」和「HOME 不可写、面板能开但装不了依赖」是两种完全不同的故障，原来共用一次探测。
- 数据目录以 `:ro` 挂载、或 NFS `root_squash` 场景下，新建 `.home` 会失败；这一句带了兜底，失败时仍然走到上面那道预检，打出「数据目录不可写 + 三条原因 + 修复命令」，而不是被 `set -e` 静默带出容器。
- PID 文件写完后 chown 给运行用户，消掉后端覆写失败那行很误导的日志。

> **已知限制**：配了 `PUID/PGID` 之后，面板里的「Linux 系统依赖」（`apt-get` / `apk`）**必然装不了**——系统包管理器要写 `/usr`、`/var/lib/dpkg` 和自己的锁，这些都需要 root。这是降权运行的固有代价（青龙同样如此），不是 bug。
>
> 这一版起，这条路会**提前拦下并给出中文说明**，而不是抛一串英文 `Permission denied`。
> 说明会按部署形态给出路：容器里提示 `docker exec -u 0 <容器名> apk add <包名>`（Debian 版镜像用 `apt-get install -y`），
> 裸机部署提示的是「以 root 手动装，或去掉 systemd 单元里的 `User=`」——给二进制部署的用户一段 `docker exec` 指引等于没给。
> **Node.js / Python 依赖不受这条限制**，降权下照常在面板里安装。
>
> 同时修掉一处更隐蔽的：**降权后点「卸载」Linux 依赖，面板会把记录直接删掉**，看起来像卸载成功，
> 而 `apk`/`apt` 一次都没跑、包还在系统里，那段中文说明也一个字都不会显示。现在改成标记失败并把原因写进日志，
> 与 Node.js / Python 两个分支的处理一致。

### Magisk Debian 版 SSH 连不上

先说清楚这一版的定位：**根因没有真机日志能坐实**。原因是 `service.sh` 里 sshd 的启动写法是
`/usr/sbin/sshd >/dev/null 2>&1 || true`——**fatal 信息 100% 被丢弃**，容器里又没有任何 syslogd，
所以你我都看不到真实报错。这一版同时做两件事：把四条候选根因全部按结构差异修掉，
并把可观测性补齐，让下一次失败能自证。

Alpine 与 Debian 在 SSH 上的实际差异（已逐条核对上游包的源）：

| 维度 | Alpine 3.18 | Debian bookworm |
|---|---|---|
| sshd 是否走 PAM | **否**（`openssh-server` 编译时 `--without-pam`，PAM 版是独立包 + 独立二进制 `sshd.pam`） | **是**（Debian 打补丁把 `UsePAM yes` 取消了注释，且 `--with-pam`） |
| 特权分离用户 `sshd` | baselayout 自带 | 靠 `openssh-server` 的 postinst 现场 `adduser --system` 创建 |
| sshd_config 顶部 `Include` | 无 | **有**，未注释 |
| 装依赖 | apk 单源约 50MB | apt 四源回退约 300MB，退出码被刻意忽略 |

四条候选根因与对应的修复：

- **旧 sshd 占着端口，新容器的 sshd 从没被启动过。**

  > `ruri` 走的是 chroot，命令行里没有 `-u`，**不建任何 namespace**——容器与宿主共享同一张进程表。
  > 而 `service.sh` 的启动去重判据是 `pgrep -x sshd`，它会命中**整机**任何叫 sshd 的进程。
  > 重装时的清理只有 `pkill -f daidai-server` 和 `pkill -f "ruri.*$rootfs"` 两条，
  > 都是按命令行字符串匹配的，而容器里 sshd 的 argv 是 `/usr/sbin/sshd`，**一条都命中不了**。
  > `rm -rf` 之后它就变成一个「根目录已被删除」的孤儿进程，监听 socket 一直活着。
  > 「先装默认的 Alpine 版试用 → 再刷 Debian 版」正好命中这条路。

  现在重装时按 `/proc/<pid>/root` 归属把落在旧 rootfs 里的进程清干净，启动去重也改成**看端口是否真的在监听**而不是看进程名。

- **`openssh-server` 没真正装成/配成，而安装期的验证清单里没有 sshd。**

  > 原来的清单只有 `python3 / node / npm / git / bash`。Debian 侧那批包约 300MB、跨四个镜像源下载，
  > 单个包 404 / 中途断网 / dpkg 停在「已解包未配置」都不会让 `apt-get install` 返回非 0。
  > 而 `sshd_config` 是 conffile，解包即落盘——于是 `service.sh` 里 `[ -f /etc/ssh/sshd_config ]`
  > 那道守卫会以为一切正常，实际上 postinst 里的「建 sshd 特权分离用户」和 `ssh-keygen -A` 根本没跑过。

  现在安装期会单独验一次 SSH（二进制 / 配置 / 特权分离用户 / host key / root 密码 / `sshd -t`），Debian 分支还会在装完后复核 `openssh-server` 的 dpkg 状态并按需 `--reinstall` + `dpkg --configure -a`。**SSH 自检失败不会中止安装**（面板 Web 不依赖它），但会明确告警。

- **PAM 会话栈在 chroot 里失败。**

  > Debian 的 `/etc/pam.d/sshd` 里有 `session required pam_loginuid.so`，它要写 `/proc/self/loginuid`。
  > `ruri` 的 `-S` 把宿主 `/proc` 直接 bind 进了容器，Android 内核又必然 `CONFIG_AUDIT=y`
  > （SELinux 依赖 audit），所以这个文件通常是**存在的**，走不到「文件不存在就 `PAM_IGNORE`」那条安全路径；
  > 写入一旦返回 `EPERM` 就是 `PAM_SESSION_ERR`，`required` 之下整条 `pam_open_session` 失败——
  > 表现正是「密码验证通过、随即 `Connection closed by remote host`」。

  现在把它降为 `optional`（容器场景的通行做法）。**刻意没有用 `UsePAM no`**：Debian 有过「构建时没链上 crypt，`UsePAM=no` 下正确密码也一律被拒」的先例，风险比降级这一条大。这段用 `[ -f /etc/pam.d/sshd ]` 做守卫，Alpine 上天然是空操作。

- **`chpasswd` 静默失败，root 其实没有密码。**

  > 两处 `chpasswd` 都是 `2>/dev/null` 且不看退出码。Debian 的 `chpasswd` 走 PAM，
  > 只要 `passwd` / `libpam-modules` 里有一个停在半装状态它就会失败，
  > root 于是保持 rootfs 自带的锁定串（`*` 或 `!`），密码登录 100% 被拒且零线索。

  现在回读 `/etc/shadow` 确认，没写进去就用 `openssl passwd -6` + `usermod -p` 兜底。（用 awk 直接读文件而不是 `getent shadow`：musl 的 `getent` 不支持 shadow 数据库，那条命令在 Alpine 上恒为空。）

另外顺手修掉一处**完全静默的失效模式**：OpenSSH 的取值规则是「**第一次出现的值胜出**」（和 nginx / Apache 的直觉相反），而 Debian 的 `sshd_config` 顶部有一行未注释的 `Include /etc/ssh/sshd_config.d/*.conf`——只要那个目录里以后有任何 `.conf`，脚本追加到文件末尾的配置就会被静默覆盖。现在同名指令会被先删净、我们的三行统一写在一处，并在存在 `Include` 时同步写一份 `00-daidai.conf`，两条路结论一致。

> **这段重写刻意避开了 `Match` 块**，因为「删净 + 追加到末尾」这个直觉做法在两个方向上都会出事：
> 删除会波及 `Match Address 192.168.1.0/24` 里那种**作用域限定**的同名指令（那是用户自己的安全策略）；
> 而只要文件尾部有一个生效的 `Match` 块，追加的三行就会落进块里，**`Port` 在 `Match` 内是非法指令**，`sshd` 直接起不来——SSH 会从「能连」变成「端口无人监听」，且每次开机都被重新写坏。
> 现在的做法是：只在**第一个生效的 `Match` 之前**做删除，并把三行插在那个位置；没有 `Match` 时行为与追加到末尾等价。

> **行为变化，需要你知道**：这三项（`Port` / `PermitRootLogin` / `PasswordAuthentication`）现在**每次开机都会按 `ports.conf` 重写**。此前只有 `Port` 是这样，另外两项只在安装时写一次。
> 这与面板 `config.yaml` 的处理是同一套逻辑（由 `ports.conf` 单向决定、不保留手改），但如果你在**全局作用域**把 SSH 改成了密钥登录、或关掉了密码认证，**下次开机会被改回来**（写在 `Match` 块里的不受影响）。
> 其余指令（`AuthorizedKeysFile`、`AllowUsers`、host key 配置等）也都不受影响，只有这三项是模块托管的。

## 排障：SSH 不通时现在能看到什么

- **点管理器卡片的「运行 / Action」按钮**，输出里新增：
  - `SSH_PORT` 的实际监听情况（此前只查了 `PANEL_PORT`，README 却一直写着两个都有）；
  - 容器 SSH 自检：`sshd` 版本、`sshd_config` 是否存在、特权分离用户、host key 数量、root 密码是否已设置、`sshd -t` 的原文；
  - 容器内 `service.log` 最近 30 行（含每次开机写的 SSH 状态快照）与 `sshd.log` 最近 30 行。
- **sshd 改用 `-D -e` 启动，日志落到 `/app/Dumb-Panel/sshd.log`**（超过 1MB 时在下一次拉起 sshd 前滚动为 `.old`）。两个参数缺一不可：没有 `-e` 日志会走 syslog 被静默丢弃，没有 `-D` 时 sshd 会 `daemon(0,0)` 把 stdio 重定向到 `/dev/null`，`-e` 就只剩 daemonize 之前那几条 fatal 还看得到。
  > 滚动刻意放在「确实要重新拉起 sshd」的分支里：老 sshd 还开着这个 fd，在它仍在跑时 `mv` 的话，它会继续往 `.old` 写，而新的 `sshd.log` 永远长不到阈值——滚动再也不会触发，`.old` 变成无上限增长。
- **启动前先跑 `sshd -t`**，配置语法、host key 可读性、特权分离用户/目录缺失这三类问题会当场落进日志。
- **启动去重与启动后复检都直接读 `/proc/net/tcp{,6}`**，不用 `nc -z`：`PATH` 里的 `nc` 有可能解析到 busybox 的 applet，它不认 `-z`，会恒定返回「没在监听」——于是每次开机都多起一个注定 `Address already in use` 的 sshd，并在日志里留下一句假告警。复检会等最多 5 秒（中低端手机上 sshd 要一两秒才加载完 host key 并 bind，只探一次会打出误导性的「端口未监听」）。
- **每次开机写一份 8 行的 SSH 状态快照**（sshd 路径 / 特权分离用户 / host key 数量 / 密码哈希前缀 / `UsePAM` / `pam_loginuid` 那一行 / drop-in 列表 / `loginuid` 是否存在），足以在事后一次性区分上面四条根因。
- 进容器那次 `ruri` 调用的输出也重定向进了宿主 `service.log`，此前是直接丢弃的。
- **容器内的 `service.log` 补上了 1MB 滚动**。宿主侧那份本来就有，这一份一直没有——而面板起不来时守护每 6 分钟就会重跑一次启动脚本，每次都要往里写十几行（这一版还多了一份 SSH 状态快照），长期跑下来会白白吃掉手机内部存储。

## 内部改动

- 模块外壳版本 `3` → `4`（`DAIDAI_MAGISK_SHELL_VERSION` 与 Go 侧的 `currentMagiskShellVersion` 同步）。
  **`requiredMagiskShellVersion` 保持 `1` 不动**——新面板在旧外壳上照常运行，不该把老用户挡在在线升级之外。
- **`docker/entrypoint.sh` 此前零测试零 CI 覆盖**，改坏了 `go test` 照样全绿。这一版补了两层：
  - `docker/test-entrypoint-puid.sh`：把 entrypoint 原样跑起来（只桩掉 nginx / find / su-exec / gosu / daidai-server），验证 **8 种 PUID/PGID 组合**下的最终 uid、gid、HOME 指向、「HOME 到底能不能写」，以及只读数据目录下有没有给出友好诊断。已接进 CI（`checks.yml`），需要 root，脚本自己会 `unshare --mount` 并给 `/tmp` 挂私有 tmpfs。
  - `server/service/docker_entrypoint_assets_test.go`：静态断言钉住关键行，其中一条锁的是「entrypoint 的 HOME 必须与代码侧回落目录是同一个」这条跨层契约。
- **新增 `scripts/check-shell-syntax.sh` 并接进 CI**：仓库里的 shell 加起来上千行却一行都不进 `go test`，少一个 `fi` 就会让开机脚本从错误点开始整段不执行，而 CI 照样全绿。这道门禁对每个 `.sh` 跑 `bash -n`，对 shebang 是 `/bin/sh` 的再跑一遍 `dash -n`，并且会把 `ruri ... -c '<脚本>'` 这类**以字符串传进容器执行**的内联脚本单独抽出来检查——它们对整文件的 `bash -n` 是完全透明的。
