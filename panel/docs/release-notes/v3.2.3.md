<!-- release-title: 修「编辑一次正在跑的任务就把它静默关掉」；把「定时任务到点不执行、还一条日志都没有」的 6 条静默路径全部翻到面板上 -->

## 版本概览

`v3.2.3` 是一个**「定时任务为什么没跑」专版**，起因是 [#115](https://github.com/linzixuanzz/daidai-panel/issues/115)：

> 3.2.2 版本，运行 playwright 调试运行没问题，添加到定时任务中就不能运行了，定时任务中也不显示日志

这一版做了两件事：

1. **修掉一个确认的真实缺陷**：编辑一个**正在运行 / 正在排队**的任务并保存，会把它从调度器里摘掉且不再挂回去 —— 这个任务从此再也不会被定时触发；更糟的是本次执行跑完时它还会被**静默判成「已禁用」**。
2. **把「任务不执行且没有日志」的 6 条路径全部变成用户看得见的信息** —— 这才是本版的主体。在此之前，这 6 条路径在面板上长得**一模一样**：任务显示「已启用」、「下次运行」列有一个像模像样的时间、日志一句「该任务还没有日志记录」。用户无从判断自己踩的是哪一条。

同时新增一篇排查文档：[定时任务不执行 / 没有日志](../task-not-running.md)，含 **Playwright / 浏览器自动化脚本**专门一节。

> **对 #115 报告者的说明**：本版**没有**声称已经定位到你那条任务的具体原因。上面 6 条里有 4 条只能靠你面板上的实际显示来区分，issue 里已经列了 4 个问题，麻烦帮忙回一下。本版做的是：**让这 4 条以后不必再问也能自己看出来**。

## 先说清楚：「该任务还没有日志记录」到底意味着什么

这句提示严格等价于一件事：**日志表里这个任务一行记录都没有**。

而任务日志是**执行器起进程的那一刻就建好的** —— 只要脚本真被拉起来过，哪怕它第一行就语法错误、哪怕解释器压根不存在、哪怕命令解析就失败了，都会留下一条**有内容的失败日志**。所以「一行都没有」只可能意味着：

> 这次执行**从来没有被调度器交给执行器**。

由此排除掉一大片方向（下面每条都在代码里核过）：

| 常见猜测 | 为什么不成立 |
|---|---|
| 脚本 / 依赖 / Python 版本有问题 | 它们要等执行器起了进程之后才有机会出问题，那时日志行早就建好了 |
| 定时任务的运行环境和调试运行不一样 | 两条链路共用同一个环境构造函数、同一个用户、同一份 `PATH`、同一份工作目录规则 |
| 命令 `task 京东直播.py` 没被解析出来 | 解析失败必然走到失败兜底，落一条「执行失败」日志 |
| 编辑器换 Monaco 之后把脚本存成 CRLF / BOM，shebang 失效 | 行尾处理只作用于 `.sh`，Python 文件逐字节原样写盘；而且面板从不靠 shebang，永远显式拉解释器 |
| 是 3.2.x 引入的回归 | `git log v3.0.0..HEAD -- server/service/scheduler_v2.go` 是**空的**；3.2.0 / 3.2.1 / 3.2.2 没有一行改动落在调度或日志创建链路上 |

**顺便说一句：「调试运行没问题」这个事实，对定位这个现象是零帮助的。** 调试运行走的是一条完全独立的轻量链路：不经过调度器、不写任务日志、不做超时和并发控制。它能证明脚本和环境没问题，**证明不了调度那一侧**。

## 升级须知

### 1. 编辑「正在运行 / 排队中」的任务，行为变了（这是修 bug）

以前：`AddJob` 会先无条件把这个任务在 cron 里的触发条目全部摘掉，**然后**才判断「状态是不是已启用」，不是就直接返回。

问题在于 `排队中(0.5)` 和 `运行中(2)` **是启用态任务的瞬时状态**，不是禁用。于是只要保存任务的那一刻正好撞上这两个瞬间，条目摘掉了、没挂回去，任务从此静默失联。撞上的机会比想象中多：

- 在任务列表点「编辑」→ 保存（后端会重新读出**真实状态**再去注册）；
- 订阅同步覆盖任务定义时；
- 备份恢复触发的全量重载时（它当时只捞 `status = 已启用` 的任务，正在跑的那条直接漏掉）。

**更坏的是复合后果**：条目没了 → 「这个任务在调度器里吗」变成否 → 本次执行结束结算时，面板把「运行中 + 调度器里没有它」判成**已禁用**。也就是说：**你只是保存了一下一个正在跑的任务，它跑完就被悄悄关掉了。**

本版把早退条件改成「**只有真正被禁用才不注册**」，并把全量重载、启动装载的查询口径一起对齐。

同时，「在运行中禁用任务、等这次跑完再生效」这个意图，以前是靠「调度器里还有没有这条任务」反推的 —— 这正是上面那条缺陷的帮凶。现在改成**显式记一笔**，语义不再依赖别的状态；放宽早退条件之后，这一笔同时充当护栏：**已经点过禁用的任务，中途任何一次注册都不会把触发条目挂回去**。少了这道护栏，被禁用的任务会带着活着的触发条目继续按点执行，比原来的缺陷更糟。

> 唯一的行为变化是「排队中 / 运行中的启用任务现在也会保留并重新注册触发条目」，这本来就是期望行为。**已禁用、以及已经点过禁用的任务仍然不注册**。

顺带把全量重载（备份恢复会触发）从「先清空再逐条重建」改成「先逐条重建、最后摘掉这次没出现的」：以前那个先清空的动作会留下一个「所有任务都查不到触发条目」的空窗口，恰好在这期间刷新任务列表，整屏都会误报「未注册到调度器」。

### 2. 任务表加了两列，接口多了三个字段（都只增不改）

`tasks` 表新增 `last_skip_at` / `last_skip_reason` 两列，由面板启动时自动补齐，**存量数据平滑升级，无需任何手工操作**。它们承载「到点了但这次没执行」的最近一次原因，详见下面「新增 2」。

接口侧对应多了三个字段：任务对象上的 `last_skip_at` / `last_skip_reason`，以及任务列表上的 `schedule_hint`（正常任务上这个 key **完全不存在**）。不认识它们的客户端行为与升级前逐字节一致。

### 3. 「最近一次日志」接口的 404 文案变了

`GET /tasks/{id}/latest-log` 在查不到日志记录时，以前一律回 `暂无日志`。现在分两种：

- 从来没跑过 → `该任务还没有日志记录`（与面板日志窗口一直显示的那句一致）
- 跑过、但日志被保留策略清掉了 → `该任务的日志已按保留策略清理（最近一次运行 …），保留天数可在设置里调整`

状态码仍是 404、响应体仍是 `{"error": ...}`，**契约没变**，变的只是那句人话。APP 侧如果对这句文案做过精确匹配需要跟一下（本仓前端已改成直接把后端这句显示出来）。

## 新增 1：任务列表会直说「这条任务其实不会自动触发」

**这是本版最有用的一项。**

在此之前，「下次运行」列显示的时间是面板**拿 cron 表达式现算**出来的 —— 表达式合法就一定算得出来，这跟「这个任务有没有真的注册进调度器」**是两回事**。两边对不上时，面板此前不会有任何表示。

现在任务列表、移动端卡片、任务详情三处都会在这种情况下给出提示，**而且分两级**：

| 什么情况 | 图标 | 提示语 |
|---|---|---|
| 任务类型是「手动运行」 | 灰色信息 | 该任务类型不会自动触发，只能手动运行 |
| 任务类型是「开机运行」 | 灰色信息 | 该任务只在面板启动时自动执行一次，不按定时规则触发 |
| 是定时任务，但调度器里没有它的触发条目 | **橙色警示** | 未注册到调度器，重新保存一次任务即可恢复 |

前两条只是在陈述任务类型、本来就该如此，用警示色天天挂着等于喊狼来了，所以给的是中性的灰色图标；只有最后一条是真故障。列表里那一列只有 160px，装不下标签，所以是图标 + 悬停提示；任务详情里地方够，整句话直接摊开写。

**不提示的两种情况**：已禁用的任务（状态列已经写着「禁用中」，再挂图标只是噪音）；以及「运行中点了禁用、等这次跑完再生效」的任务 —— 它的触发条目确实已经被摘掉了，但那正是用户要的，这时候提示「重新保存一次即可恢复」等于在教用户把自己刚关掉的任务重新打开。

最后那句给的处理办法是**实测过的**：打开任务编辑弹窗、什么都不改直接保存，触发条目就会重新挂上去，图标随之消失。

## 新增 2：被「不允许多实例」拦下的触发，现在会留下记录

这是整个调度链路上**唯一一处「接口返回正常、却既不执行也不留任何痕迹」**的分支：上一次执行还在跑，且任务没勾「允许多实例」，本次触发被直接丢弃，以前只在面板后台打一行英文日志。

用户侧看到的就是：到点了什么都没发生 / 点了运行提示「任务已启动」却毫无动静，日志一片空白。

现在这种情况会记在**任务本身**上。打开任务详情，会多出一行 **「最近一次被跳过」**，写着时间和原因：

> 2026-09-06 11:42:47　上一次执行仍在进行中，且该任务未开启「允许多实例」，本次触发没有执行

**为什么不在日志里加一条**（这版本来是那么做的，实测后改掉了）：跳过意味着这次**压根没执行**。给它建一条任务日志会连带三处副作用 ——

1. 混进仪表板的「已终止」统计和成功率口径，而它根本不是一次执行；
2. 耗时是 0，会把任务耗时统计一起拉歪；
3. 最要命的是**它的时间比被它阻塞的那次执行更晚**，于是它成了「最近一次日志」—— 你点开日志想看上次到底跑了什么，看到的却是一句「本次触发被跳过」。

记在任务行上就没有这些副作用，而且天然只保留最近一次：一个每分钟触发的任务卡上三小时，也不会刷出一百八十条记录，更不需要任何去重逻辑（反复写的是同一行）。

顺带修了同一分支的一个小问题：被拦下时任务状态没有从「排队中」放回去，会一直停在排队中假象上。

> 「队列满」那条分支仍然只走面板日志（下面「新增 5」）：它是高频瞬时状态，往任务上写反而会不停覆盖真正有价值的原因。

## 新增 3：日志窗口不再把「还在排队」谎报成「还没有日志记录」

以前日志窗口拿不到日志时会快速重试 5 次（总共 2.5 秒），用完就把「该任务还没有日志记录」**定死**，之后再也不会自己纠正。

但任务这时完全可能只是**还在排队**：设了随机延迟的任务走的是「延迟后重新入队」，并发数被别的任务占满时也一样，这段窗口里日志表里确实一行都没有。**这正是 #115 截图里那一屏的形态。**

现在改成**按任务状态**决定要不要继续等：任务还停在「排队中 / 运行中」就按 1 秒一次继续轮询（60 次兜底上限），期间显示的是

- 排队中 → 「任务排队中，开始执行后会出现日志…」
- 运行中 → 「任务已开始，正在等待第一条日志…」

头部徽标同步显示「等待中」，底部状态栏显示「等待日志中」，并明确告诉用户「出现后会自动显示，不用手动重开」。日志一出现自动切回正常显示。

顺带修掉一处长期存在的文案矛盾：空态下那行小字以前是写死的「任务执行一次后就会出现日志」，于是「日志已过期，文件已被清理」这种**明明跑过**的情况，底下也跟着说「执行一次后就会出现」—— 同一块区域里两句话自相矛盾。现在这行小字跟着上面那句一起变，对不上就不显示。

## 新增 4：日志被保留策略清掉时，直说是被清掉的

日志清理是**物理删除**（默认保留 7 天，设置 → 任务运行 → 「日志删除频率」）。删完之后任务行上的「上次结果」还在，于是会出现这种组合：列表里明明写着「成功」，点开日志却说「还没有日志记录」—— 同一屏里两个互相矛盾的说法，很容易把「跑过、日志被清了」误判成「从来没跑过」。

现在这种情况直接说明是被保留策略清理的，并带上最近一次运行时间。

## 新增 5：三处静默跳过改成中文日志，注册失败不再被丢掉

调度器决定「这次不跑」时，以前只在后台打一行英文，面板日志页里既不好搜、也不会被判成警告/错误级别。现在这三处都换成中文（面板日志会据此自动判级，直接在**设置 → 面板日志**里可见可搜）：

| 场景 | 现在的日志 |
|---|---|
| 上一次还在跑、未开多实例 | `任务 12 本次触发被跳过：上一次执行仍在进行中，且该任务未开启「允许多实例」，本次触发没有执行` |
| 定时触发时队列满 | `任务 12 定时触发入队失败（本次不会执行）: task queue is full` |
| 随机延迟结束后重新入队失败 | `任务 12 随机延迟结束后重新入队失败（本次不会执行）: …` |
| 开机任务入队失败 | `开机任务 12 入队失败（本次不会执行）: …` |
| 面板启动时装载失败 | `任务 12 启动时注册调度失败（它不会自动触发）: …` |
| 全量重载时注册失败 | `任务 12 重新注册调度失败: …` |

另外，**新建任务**与**订阅自动建任务**这两处，注册调度返回的错误此前是被整个丢掉的，接口照样回「创建成功」。今天这条错误出口恰好走不到（新建时的 cron 校验和注册时用的是同一个解析器，判定必然一致），但这纯靠两处代码碰巧同源维持，没有任何测试钉住。现在补上日志。

> 刻意**不**改成返回 500：任务已经落库了，报错回滚对用户更难解释。用户侧的可见性由上面的 `schedule_hint` 承担。

## 新增 6：新建任务后会告诉你「下次什么时候跑」，并可以直接先跑一次

这条针对的是 #115 里**最可能的真实处境**。

从「脚本管理 → 添加到定时任务」建出来的任务，预填的定时规则是 **`0 0 0 * * *`，也就是每天 00:00**。于是：用户在脚本页刚看完调试运行的完整输出，转手加成定时任务，接下来**最长 24 小时什么都不会发生**，日志窗口如实显示「该任务还没有日志记录」—— 全程没有任何错误，但看起来就像面板坏了。

以前创建成功只弹一句「任务创建成功」。现在会明确告诉你下次运行时间，并给一个「立即运行一次」的入口：

> 任务已创建，下次运行时间：09-07 00:00:00。要现在先跑一次吗？　　[ 知道了 ] [ 立即运行一次 ]

「手动运行 / 开机运行」类型算不出「下次」，换成对应的说法（它们不会自动触发）。

同时把散在四处的默认 cron 字面量收敛成两个具名常量（脚本入口 / 表单新建、切换定时类型的兜底、规则行新增各写各的，改一处忘一处的风险一直在）。**每一处的取值都与改动前逐字节一致** —— 改默认值是产品决定，不该顺手夹在修 bug 里。

## 新增 7：一篇排查文档

[定时任务不执行 / 没有日志](../task-not-running.md)，写给遇到这个现象的用户，从上往下一条条过即可：

1. 看「定时规则」列 —— 是不是被建成了「手动运行 / 开机运行」
2. 看「下次运行」列旁边有没有**橙色**警示图标 —— 有没有真的注册进调度器（灰色的只是在说明任务类型）
3. 确认时间是不是还没到 —— 从脚本页加的任务预填每天 00:00
4. 看「状态」列是不是停在「运行中」 —— 上一次卡住会挡住后面每一次触发（任务默认**不设超时**）
5. 「上次结果」有值但日志说没有 —— 日志被保留策略清了
6. 翻面板日志 —— 搜「跳过」「入队失败」「注册调度失败」

外加**「关于 Playwright / 浏览器自动化脚本」**一节，说清三件容易踩的事（都已核实）：

- 面板镜像**不预装** Playwright，也不预装 Chromium 及其运行库，要自己装 `playwright` 包 + `playwright install` + `playwright install-deps`；
- **Alpine 版镜像跑不了浏览器**（musl 环境，Playwright 官方下载的 Chromium 是 glibc 构建的），要跑浏览器自动化请用 **Debian 版镜像**；
- 容器 `/dev/shm` 默认只有 64MB，Chromium 很容易因此崩，`--shm-size=1g` 或 `--disable-dev-shm-usage`。

## 验证到什么程度

- 后端 `go test ./... -count=1`：11 个包全绿。新增 3 个测试文件、1 个既有回归文件加了用例，其中钉死的关键行为包括：
  - 排队中(0.5) / 运行中(2) 的任务调 `AddJob` / `UpdateJob` 后触发条目仍在；已禁用的仍然不注册；手动 / 开机任务仍走「空登记」；
  - **编辑一个正在运行的任务后，本次执行结束不会被判成已禁用**（改动前这条断言必然失败）；
  - **已经点过禁用的任务，中途再被注册也不会把触发条目挂回去**；
  - 待禁用标记不会漏到「复用了同一个 id 的新任务」上（标记只活在内存里，而 SQLite 的自增 id 删掉最大那行之后是会被复用的）；
  - 全量重载不再漏掉排队中 / 运行中的任务；
  - 跳过原因写在任务行上、**一条 task_logs 都不产生**，且「最近一次日志」仍然是那条真正在跑的记录；
  - `schedule_hint` 的四种情况（手动 / 开机 / 未注册 / 正常），以及「已禁用不提示、待禁用不提示、调度器没起来时不误报」；
  - 「最近一次日志」两种 404 文案。
- 前端 `npm run build`（含 `vue-tsc`）通过。
- **起了一套真实实例逐项实测**（不是只看代码）：
  - 直接往库里塞一条「没走过接口、因而没注册进调度器」的定时任务 —— 列表如实显示「已启用 + 有下次运行时间 + 橙色警示图标」，提示语正确；手动 / 开机任务拿到的是灰色信息图标；
  - 按提示重新保存一次，图标消失、触发条目挂回去了；
  - 造出「被跳过」的现场，任务详情里如实显示「最近一次被跳过 + 时间 + 原因」；
  - 从脚本页「添加到定时任务」，预填确认是每天 00:00，创建后确认弹窗与「立即运行一次」都正常；
  - 日志的三种状态：排队中（等待态 + 自动轮询）、从来没跑过、日志被保留策略清掉，文案逐条核对；
  - **升级路径**：把两个新列从库里删掉、重启面板，确认自动补回且数据完好。

## 本版没做的

- **没有**改默认 cron 表达式的取值（只消灭了「切换定时类型再切回来落到第三个值」这种不一致）。
- **没有**给「队列满」等其它跳过场景在任务上留痕（它是高频瞬时状态，会不停覆盖真正有价值的原因），它们走面板日志。
- **没有**为「跳过」建任务日志行（原因见上面「新增 2」）。
- **没有**把「注册调度失败」改成接口报错回滚。
- **没有**在镜像里预装 Playwright / Chromium（体积代价过大，交给按需安装，文档已写清怎么装）。
- **没有**改动 Magisk 模块外壳脚本，也**没有**改动 Docker entrypoint、Dockerfile 与 `docker/nginx.conf`。

## 关于 APP

本版**没有** APP 侧改动，APP 不需要跟随升级。

接口面只有两处变化，都是安全的：

- 任务对象多了 `last_skip_at` / `last_skip_reason`，任务列表多了一个**可选**字段 `schedule_hint`（正常任务上这个 key 完全不存在）。APP 不认识就不读，行为与升级前逐字节一致。API 文档已同步。
- `GET /tasks/{id}/latest-log` 的 404 **文案**变了（状态码与响应体结构没变）。如果 APP 对「暂无日志」这四个字做过精确匹配，需要跟一下；改成直接显示后端返回的 `error` 字段即可，本仓前端就是这么改的。

## 升级方式

| 部署方式 | 操作 |
|---|---|
| Docker | 重新拉取镜像后重建容器（本版没有改动 entrypoint 与 Dockerfile） |
| Magisk 模块 | 面板内一键更新即可（本版**没有改动模块外壳脚本，不需要重刷 ZIP**） |
| 裸机 / Windows | 面板内一键更新，或下载新版二进制替换 |

本版给 `tasks` 表加了 `last_skip_at` / `last_skip_reason` 两列，由面板启动时**自动补齐**，存量数据平滑升级、行为逐字节不变，无需任何手工操作（已实测：把列删掉再重启，面板会自动补回）。

**升级后值得看一眼的地方**：打开定时任务列表，看看「下次运行」列里有没有任务带上了**橙色**警示图标 —— 如果有，说明它此前就已经处于「显示已启用、实际不会触发」的状态了，按提示重新保存一次即可。（灰色图标只是在说明这是手动 / 开机运行任务，不用管。）
