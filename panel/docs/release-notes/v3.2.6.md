## 版本概览

`v3.2.6` 收三个来源的需求：[#119](https://github.com/linzixuanzz/daidai-panel/issues/119) 的 2 条、[#120](https://github.com/linzixuanzz/daidai-panel/issues/120) 的 1 条（拆成 2 件事做），外加一条会话里补充的定时规则需求。**一条不落全做了。**

其中有两条查下来发现「面板其实早就支持，只是用户看不见」——这种情况没有当成「不是 bug」关掉，而是去修**为什么看不见**。下面逐条说清楚。

## 需求 1：定时规则不支持「9 点到 22 点每 10 分钟」，加上「工作日」也不支持

> 定时规则好像不支持 比如我要设置 早上9点到晚上10点 每10分钟执行一次 这样的 如果要在加上工作日也不支持

**先说结论：`0 */10 9-22 * * 1-5` 这条表达式，面板一直就能存、能校验、也确实只在工作日 9 点到 22 点之间每 10 分钟跑一次。** 调度器从来没有问题。

那为什么用户会认为不支持？三条原因叠在一起：

### 原因一：面板会给出一句自信的错误描述

规则输入框下面那个绿色徽标，写的是后端翻译出来的人话。而翻译器有个「早退」逻辑：只要分钟段是 `*/10`，它立刻返回「每10分钟」并**丢掉后面所有字段**——小时区间 `9-22` 和工作日 `1-5` 被整段吃掉。

用户敲完正确的表达式，看到面板说「每10分钟」，只会得出一个结论：**面板没认出我写的时段和星期**。

这比含糊更坏。代码里其实早就有人意识到这类问题，还专门为「逗号小时列表」那条分支加了守卫并写下注释：「不守 dow 的话会变成【自信的错误】，比含糊更坏」——只是那个守卫在早退逻辑**之下**，永远轮不到。

### 原因二：出厂预设里根本没有这种形态

改前那 21 条出厂预设里，**没有任何一条含小时区间**——步进要么在秒段（`*/10 * * * * *`）、要么在分段（`0 */10 * * * *`）、要么在时段（`0 0 */2 * * *`），而步进一出现，小时/日/月/星期这几段就全是敞开的。「工作日」分类更是只有 `0 0 9 * * 1-5` 和 `0 0 18 * * 1-5` 两条整点。也就是说预设面板里翻遍了也找不到一条「时段 + 步进」，而选中任何一条预设都是**整条覆盖**，没法与时段叠加。

### 原因三：所谓的「定时规则编辑器」根本不是编辑器

`CronInput` 一直是「一个文本框 + 常用规则弹窗 + 随机时间弹窗」。**没有任何分/时/星期的选择控件**。不会写 cron 的人只能手打，随机时间弹窗的「时间窗」也只是离散抽样范围，永远产出不了 `*/10` 或 `9-22`。

### 改成了什么

**1）中文描述改成「看全字段」。**

翻译器不再只看一段就下结论。新的输出：

| 表达式 | 改前 | 改后 |
|---|---|---|
| `0 */10 9-22 * * 1-5` | 每10分钟 | **工作日 9-22 点，每 10 分钟** |
| `0 */10 9-22 * * *` | 每10分钟 | **每天 9-22 点，每 10 分钟** |
| `0 */10 9-22 * * 0,6` | 每10分钟 | **周末 9-22 点，每 10 分钟** |
| `0 0 9-22 * * 1-5` | 自定义 cron 表达式 | **工作日 9-22 点整点** |
| `0 30 9-22 * * *` | 自定义 cron 表达式 | **每天 9-22 点，每小时第 30 分钟** |

顺带修掉四条一直存在的错误描述——出厂预设「工作日9点」`0 0 9 * * 1-5` 以前被说成「每天 09:00」，现在是「工作日 09:00」；「周末10点」「每周一0点」同理。以及预设「每小时」`0 0 * * * *` 自己打自己的脸的问题：预设面板写着「每小时整点执行」，选中后徽标却退化成「自定义 cron 表达式」，现在两边都是「每小时整点」。

**认不出的一律落兜底，绝不猜。** `MON`、`1-5/2`、`9-22/2`、`9-11,21` 这些写法合法但翻译器认不出，就老老实实显示「自定义 cron 表达式」——含糊，但不会撒谎。

**2）新增三条出厂预设**（都在「常用规则」弹窗里）：

| 名称 | 表达式 |
|---|---|
| 每天9-22点每10分钟 | `0 */10 9-22 * * *` |
| 工作日9-22点每10分钟 | `0 */10 9-22 * * 1-5` |
| 工作日9-18点每30分钟 | `0 */30 9-18 * * 1-5` |

> ⚠️ **`9-22` 是闭区间**：22 点这一小时照常执行，最后一次是 **22:50** 而不是 22:00。这是 cron 本身的语义，不是面板的选择。想要 22:00 收尾，把结束小时改成 21 点再加一条 `0 0 22 * * 1-5`（定时规则本来就支持多行）。预设的说明文字里也写了这句。

**3）真的做了一个可视化编辑器。**

规则行右侧多了第三个入口「可视化编辑」（与「常用规则」「随机时间」并列）。点开是一个弹窗：

- **频率**：每分钟 / 每小时 / 每天 / 每周 / 每月 / **按时段间隔**（最后一个是这次需求的主角）
- **分钟**：每 N 分钟 / 固定第 N 分钟 / 多选
- **时段**：全天 / **时段区间**（9 至 22）/ 每 N 小时 / 指定小时（多选）/ 固定单点
- **星期**：每天 / **工作日** / **周末** / 自定义（勾选周日~周六）
- **包含秒段**：开关（关掉产出 5 段表达式）
- **实时预览**：表达式 + 一行人话 + 闭区间提示

配「按时段间隔 + 每 10 分钟 + 9 至 22 + 工作日」，预览就是 `0 */10 9-22 * * 1-5`。「定时停止」那一栏也接了同一个弹窗。

三条设计上的取舍，都是刻意的：

- **认不出的表达式绝不硬解。** `L` / `W` / `#` / 英文星期 / `9-22/2` / 混合形态，一律显示一条橙色警告「当前表达式无法用可视化表示，点应用会覆盖原表达式」，而不是猜一个模型出来悄悄改掉你手写的东西。
- **跨零点直接拒绝。** 时段选「22 至 6」会红字提示「请拆成两条规则」并禁用应用按钮——单条 cron 表达不了跨零点，偷偷帮你展开成两条会让界面上的时间窗和实际规则对不上。
- **「每月几号」和「星期几」互斥。** cron 里这两段同时被限定时取的是**并集**不是交集（`0 0 0 5 * 1-5` 实际是「每月 5 日**或**每个工作日」都跑）。可视化里让用户以为是 AND 会配出完全不同的调度，所以用频率把它们互斥掉了。

## 需求 2（#119）：订阅的两个自动开关要能单独设

> 订阅管理设置中，能否将自动添加定时任务和自动删除失效任务这两个开关也像覆盖拉取一样，让每个订阅可以独立设置开关？

这两个开关此前是**全局配置 + 订阅级布尔列**用 `或` 连起来的：`订阅开 || 全局开`。因为全局默认是开，所以那两个订阅级布尔列基本是空转的，而且**它表达不了「全局开、这一条强制关」**。

这不是新发现的问题：仓库的后端规范文档里有一张表，`subscriptions.auto_add_task` 正是被点名的「OR 语义反面教材」。这一版把它改掉了。

### 改成了什么

两个开关都变成**三态**，和「覆盖拉取」完全同构：

| 档位 | 含义 |
|---|---|
| 跟随全局设置 | 用「订阅设置」弹窗里的全局默认值（后面会显示「（当前：开/关）」） |
| 强制开启 | 不管全局怎么设，这条订阅一定建 / 一定删 |
| 强制关闭 | 不管全局怎么设，这条订阅一定不建 / 一定不删 |

全局那两个开关的名字也跟着改成「自动添加定时任务（**默认**）」「自动删除失效任务（**默认**）」，说明里写清「未单独设置的订阅使用此默认值」——与「覆盖拉取（默认）」的措辞对齐。

**这两项对单文件订阅同样生效**，这一点和只对 git 仓库订阅生效的「覆盖拉取」「完整检出」不同（订阅的任务同步逻辑本来就不分类型）。所以表单里没有给它们加 `git-repo` 的显示条件。

### 升级后行为不变

存量订阅里 `auto_add_task = 1` 的那批（凡是用「识别 ql 命令」建的订阅都是），在旧的 OR 语义下是**恒开**的。所以升级时做了一次性迁移：把这批行提升成「强制开启」，**同时把旧的布尔列清 0**。

两条 SQL 必须成对——只提升不清 0 的话，用户之后把它改回「跟随全局」，下次重启会被再次提成「强制开启」，而且没有任何报错。这条幂等性有专门的迁移测试钉着。

其余订阅落「跟随全局」，与升级前逐字节一致。

> 旧的 `auto_add_task` / `auto_del_task` 两个字段**保留但已废弃**，具体分三种情况，请按这个来：
>
> - **响应里仍然下发**，但因为再没有任何写入路径能把它们写成 `true`，它们**恒为 `false`**；
> - **`PUT` 不再接收**——这两个键已从更新白名单里移除，传了会被静默忽略（接口仍返回 200）；
> - **`POST` 只在没给三态字段时**才把 `true` 翻译成 `auto_add_task_mode=enabled` 再落库；同时给了合法三态时以三态为准。
>
> 之所以要把源列彻底堵死：启动时那次一次性回填的幂等性，全靠「源列此后恒为 0」这一条。只要还留着任何写入路径（哪怕只是网页表单把读到的值原样回传），用户手动改回「跟随全局」就会在下次重启被再次提成「强制开启」，而且不会有任何报错。

## 需求 3（#119）：Monaco 编辑器的代码正文改回黑色

> 最新的v3.2.5版本更新后，Monaco编辑器的代码字体颜色变成了一种深蓝的颜色，能否改回黑色，主题和之前的版本v3.1.1一样

**先更正一个时间点**：这不是 v3.2.5 引入的，是 **v3.2.2**（引入 Monaco 双引擎那一版）。用户从 v3.1.1 直接升到 v3.2.5，第一次看到而已。

### 根因

v3.2.2 给 Monaco 写了一套自定义主题，其中有一条：

```ts
{ token: 'identifier', foreground: '001080' }
```

看起来只是给「标识符」上色，但 Monaco 的 Monarch 语法里，JS / TS / Python 的 tokenizer 都是 `"@default": "identifier"` —— **所有非关键字的词**（变量、函数名、属性、模块名、内置函数）全部吐 `identifier`。所以这一条等于**把代码正文整片染成 `#001080` 深蓝**。

而 v3.1.1 时 Monaco 主题的 `rules` 是空数组，正文走 `editor.foreground`，也就是 `#111827`——用户说的「黑色」。

### 改成了什么

删掉那条规则。删掉之后 `identifier` 在主题里没有任何条目，内置的 `vs` / `vs-dark` 也没有，于是它落回 `editor.foreground`：**浅色 `#111827`、深色 `#e5e7eb`**，与 v3.1.1 逐字相同，并且仍然跟随你在系统设置里自定义的编辑器前景色（**没有写死 `#000000`**，那会让自定义前景色失效）。

CodeMirror 那边同一份调色板里也有一条同色规则（裸的 `variableName` / `propertyName` / `labelName`），一并删掉了——不然在齿轮菜单里切一下引擎，变量名的颜色就会变，而这个仓库有一条白纸黑字的设计契约：「两个引擎看起来是同一个编辑器」。

> 没有动的：shell 脚本里 `$VAR` 的深蓝（那是 Monaco 内置 `vs` 主题的 `variable: #001188`，v3.1.1 也是这个色，动了才是偏离）；注释、关键字、字符串、数字这些本来就与内置主题一致的规则；以及类名、正则、注解这些命中面很窄的 token。

## 需求 4（#120）：Alpine 下装不上 opencv-python

> 默认呆呆是阿帕奇镜像，能否在依赖管理增加安装依赖功能，通过apk命令装到容器里，或者提供网页版命令行用户自行操作

用户贴的日志是 pip 构建 wheel 失败。他提了两条出路，这一版**两条都做了**——但先说一件让人意外的事：

### 「通过 apk 装到容器里」这个功能，面板早就有

依赖管理页一直有 **Linux 页签**，后端支持 `apk` / `apt` / `dnf` / `yum` / `microdnf` / `zypper` 六种包管理器，还会在第一次安装前自动把源换成阿里云。

**那为什么用户不知道？** 四条原因，每条都能查证：

1. README 的功能列表原文是「可视化安装/卸载 **Python (pip) 和 Node.js (npm)** 依赖」——**一个字没提 Linux**。这是绝大多数用户唯一会读的入口。
2. Linux 页签上只写「Linux」两个字。新建依赖的输入框提示是通用文案，没有任何地方告诉用户「这里装的就是 apk/apt 系统包」，更没有 `build-base` 这类示例。
3. `docs/` 下没有一篇讲这个页签怎么用。
4. **最要命的一条**：pip 编译失败时，面板给出的提示是「**请切换到 Debian 版镜像**」。用户按提示只会去换镜像，自然永远发现不了 Linux 页签能救他。

### 改成了什么

**1）把已有的能力讲清楚。**

- Linux 页签下新增环境说明：当前探测到的包管理器、发行版、镜像源是否可配，并写明「这里装的是系统包（apk/apt），不是 Python/Node 包」。
- 新建依赖选 Linux 时给出 root 权限预警，输入框提示换成真实示例。
- **新增「安装编译工具链」一键入口**：点一下把 `build-base`、`linux-headers`、`cmake`（Debian 是 `build-essential`、`cmake`）预填进新建弹窗。探测不到包管理器时按钮禁用并说明原因。
- README 的功能列表补上 Linux 系统包，并新增一节「pip 装某个包报 gcc / CMake 相关错误怎么办」。

**2）新增「缺 C/C++ 编译工具链」失败归因，并把两条出路并列给出。**

原来的提示是二选一的：要么「换 Debian 镜像」、要么什么都不说。这一版把两条出路摆在一起，因为**它们各自对一半**：

- **换 Debian 版镜像**：对 `opencv-python` 这类包是**正确解**——PyPI 上它有 manylinux 的 x86_64 / aarch64 预编译包、没有 musl 版，换过去 pip 直接下载安装，根本不用编译。
- **装编译工具链现场编译**：对「连 manylinux 包都没有」的包才是唯一出路。**注意完整版镜像（`latest-full` / `debian-full`）也不含 `cmake`** —— 这一点 README 里也补上了，光换成完整档解决不了 opencv 这类需要 CMake 的包。

所以现在两条提示互相指路：命中「缺编译器/CMake」时会先建议换 Debian 镜像（多数科学计算包换过去就能直接装），再给出装 `build-base` / `linux-headers` / `cmake` 的现场编译方案并提醒把依赖安装超时调大；命中「musl 缺预编译包」时也会补一句「若换镜像后仍报编译失败，说明连 manylinux 包都没有，需要装编译工具链」。

> 降权部署（配了 `PUID`/`PGID`）时的文案也改了。原来会先叫用户「去 Linux 页签装」、紧接着说「非 root 无法安装 Linux 系统依赖」——用户真去点会白白多出几条失败记录、侧栏角标还会 +N。现在「装哪些包」和「去哪儿装」是分开说的：非 root 时直接告诉你面板内装不了，只能 `docker exec -u 0` 或去掉 PUID/PGID。

**3）真的做了网页版命令行。**

依赖管理页工具条菜单里新增「**系统命令行**」（仅管理员可见），点开是一个全屏终端：左边输入命令、右边实时输出、底部运行 / 停止，还带几个常用命令的快捷按钮（`apk add build-base linux-headers cmake` 就在里面）。

表头会直接告诉你三件事：当前是不是 root、探测到的包管理器是什么、单条命令的超时是多少分钟。

**边界写在界面上，不藏着**：一次一条命令（可多行，`cd /x && ls` 有效）、**不是交互式终端**、**不保留 `cd` 与变量状态**、工作目录是面板的脚本目录。

**三道护栏**，一道都没省：

| 护栏 | 做法 |
|---|---|
| **执行超时** | 新增系统配置「系统命令行超时(分钟)」（默认 30，区间 1-720，在设置页「任务执行」卡片里）。到点终止**整个进程组**，并在日志里写明是超时终止 |
| **权限** | `admin` 专属，且**刻意不挂 OpenAPI 授权**——应用令牌一律 403。这是「在面板里跑任意系统命令」，只允许登录管理员本人 |
| **审计** | 每次启动、超时终止、手动停止都写面板日志（谁、什么时候、跑了什么，命令过长会截断并标明）。**不写进任务日志表**——那张表只装真正执行过的定时任务 |

> **命令里带后台进程（`&` / `nohup`）时的行为，写在界面上了**：不重定向输出的话，孙进程会继承输出管道。面板会在命令本体退出约 2 秒后自行收尾（记成功），并在输出末尾追加一行「命令已结束；仍有后台进程持有输出管道，后续输出不再收集」——此后面板不再收集它的输出，**也不会在你关闭弹窗时把它杀掉**。命令**还在跑**的时候关窗或到超时，才会终止整个进程组。想干净利落就自己重定向：`nohup xxx >/dev/null 2>&1 &`。真要留常驻进程，建议用脚本管理 / 定时任务，别用命令行起。

> 顺带说明：`/scripts` 那条「运行代码 → Shell」的老路径**没有动**（它是 operator 权限、且没有超时）。收紧它是行为变更，会影响现有用户，留到以后单独评估。

## 顺带修掉的

- **依赖列表那一列「版本」删掉了。** 它对三种依赖类型都恒定显示 `-`——依赖模型里根本没有 `version` 这个字段。真要展示版本得让后端在安装成功后回写，那是另一件事。
- **单条命令 / 单次调试运行的输出加了上限（20 万行）。** 此前完全没有上限：实测跑 2 秒 `yes` 就能灌进 2500 万行、吃掉 1.3GB 堆内存，而默认超时是 30 分钟——容器会被 OOM Killer 干掉，**整个面板连同所有定时任务一起没**。现在超限会成块丢弃最前面的一段并在顶部标明省略了多少行。
- **修掉一处会让运行永久卡死的死锁。** 输出里出现超过 1MB 的单行（`base64 -w0 某个db`、`cat` 一个压缩成一行的 js）时，日志扫描器会停读，导致进程等待永不返回——**连超时终止都救不回来**。现在会追加一行「输出行过长，该行及其后续输出已被丢弃」并把管道排空。这条修在共享代码上，脚本调试与「运行代码」也一起受益。

## 接口变化

| 变化 | 说明 |
|---|---|
| 订阅新增 `auto_add_task_mode` / `auto_del_task_mode` | 取值 `inherit` / `enabled` / `disabled`，不传或传非法值一律按 `inherit`；**对单文件订阅同样生效** |
| 订阅的 `auto_add_task` / `auto_del_task` | **已废弃**：响应仍下发（恒为 `false`）；**`PUT` 白名单已移除，传了被忽略**；`POST` 在缺三态字段时把 `true` 翻译成 `mode=enabled` |
| 新增 `GET /api/system/console/meta` | 命令行环境元信息（是否可用、包管理器、是否 root、超时分钟数） |
| 新增 `POST /api/system/console/run` | 提交一条命令，返回 `run_id` |
| 新增 `GET /api/system/console/run/:run_id/logs` | 轮询输出，与脚本调试的日志接口同形 |
| 新增 `PUT /api/system/console/run/:run_id/stop` | 停止 |
| 新增 `DELETE /api/system/console/run/:run_id` | 清除运行记录 |
| 新增系统配置 `console_timeout_minutes` | 默认 30，区间 1-720 |

命令行那 5 条接口都是 `admin` 专属，**不接受应用令牌**。API 文档已同步。

## 验证到什么程度

- 后端 `go build ./...`、`go vet ./...` 通过；`go test ./... -count=1` **11 个包全绿，连跑三轮**。前端 `npm run build`（含 `vue-tsc -b`）通过。
- 新增/改写的用例钉住了：cron 描述的守卫（`*/N` 秒不能被说成确定时刻、星期认不出必须落兜底、`?` 不能漏进中文）、24 条出厂预设的描述快照、订阅三态的迁移幂等与「强制关闭 + 全局开 = 不建任务」的端到端、依赖归因的优先级与不误伤、命令行的权限矩阵（operator / viewer / 带 `system` 授权域的应用令牌全 403）、超时结算、注册表淘汰、日志成块截断后的全局行号连续性。
- **改动落地后做了三轮对抗性代码审查**，每一条结论都另派独立审查员逐条尝试证伪，只有判定 CONFIRMED 的才修：
  - 第一轮 7 条（2 条 high）。其中两条是本轮自己引入的：cron 的秒段守卫没有下游接手，`*/2 0 10 * * *` 从「每2秒」退化成「每天 10:00」；命令行遇到 `nohup xxx &` 这类后台进程会一直显示「运行中」，30 分钟后把用户的进程连锅端掉却报**成功**，关闭弹窗更是当场 SIGKILL。后者是审查员把复刻程序交叉编译丢进 WSL 用真 bash 实测复现的（Windows 上复现不出来 —— WSL 转发器不把 Windows 的管道句柄传给 Linux 侧进程，只在开发机上验会误以为没问题）。
  - 第二轮 6 条（+1 条被证伪驳回），只找「为了修 A 而改坏 B」。最值钱的一条：订阅那次「一次性回填」其实**每次启动都跑**，而旧布尔列仍然可写 —— 网页表单保存时会把 `auto_add_task: true` 原样回传，于是用户显式选的「跟随全局设置」会在下次重启被静默改回「强制开启」并真的开始建任务。用面板自己的青龙导入 + 自己的网页表单就能复现。
  - 第三轮 4 条，全部是**文档与代码不符**（发布说明与 API 文档里关于旧布尔字段、后台进程行为的描述没跟上修复），零代码缺陷。
- 有一条既有的偶发用例（`TestTaskListOmitsScheduleHintForTasksPendingDisable`）在全量跑里偶尔变红。用 `git worktree` 拉了一份**改动前**的树做对照实测：基线 8 轮挂 1 次、带本轮改动的工作区 8 轮 0 次，且它落在本轮一行都没碰过的 `task_query.go` / `scheduler_v2.go` 上，依赖包级全局的调度器状态 —— **是既有的时序敏感用例，不是本轮引入的回归**。

## 本版没做的

- **没有**引入 xterm.js / WebSocket / 交互式 PTY。命令行是「一次一条、看输出、能停止」，不是真终端 —— 演示站是纯静态托管，PTY 演示不了，成本也远超收益。
- **没有**收紧 `/scripts` 那条「运行代码 → Shell」的老路径（它是 operator 权限、且至今没有超时）。收紧它是行为变更，会影响现有用户，留到以后单独评估。
- **没有**把编译工具链塞进精简镜像 —— `Dockerfile` 里有构建期断言明确拒绝，那是设计意图不是疏忽。也没有往完整档里加 `cmake`（镜像会明显变大，是独立决策）。
- **没有**做「脚本跑挂时自动装 Linux 系统包」。那会让脚本执行链路触发 root 级系统写入。
- **没有**给可视化编辑器加秒段控件，所以「每10秒」「每30秒」这两条秒级预设点「可视化编辑」会看到一条橙色警告（点应用会覆盖原表达式）—— 这是「认不出就不猜」的代价，不是 bug。
- **没有**动 `stop_schedule`（定时停止）至今零校验、以及导入多行 cron 会被判非法这两个既有缺陷，也没有修描述器里 `?` 漏进「每年/每月」文案、以及 cron 的 dom/dow 是**并集**却被描述成交集这两条老问题。都是独立立项。
- **没有**补齐依赖管理 API 文档上一直欠的 11 条端点（cancel / log-stream / export / batch-delete / batch-reinstall / mirrors×2 / python-runtimes×2 / pip / npm）。
- **没有**引入任何新的前端依赖，**没有**改动 Magisk 模块外壳脚本、Docker entrypoint、`Dockerfile` 与 `docker/nginx.conf`。

## 关于 APP

系统命令行的 5 条接口不接受应用令牌，APP 完全不受影响。但**订阅这边有一处接口移除，APP 需要跟一下**——本版不是纯增量，这里说清楚：

> ⚠️ **`PUT /api/v1/subscriptions/:id` 不再接受 `auto_add_task` / `auto_del_task`。** 若 APP 的订阅编辑页仍在提交这两个布尔，从本版起是**静默无效**：接口照旧返回 200「更新成功」，但一次数据库写都没有，面板照旧按 `auto_add_task_mode` 的值行事。用户会看到「点了保存、提示成功、行为没变」。
>
> 同时 APP 读到的 `auto_add_task` / `auto_del_task` 现在**恒为 `false`**（迁移把旧布尔列清 0 了），所以一条「强制开启」的订阅在 APP 上会显示成「关」。
>
> 要正确显示与修改，都必须跟进 `auto_add_task_mode` / `auto_del_task_mode`（取值 `inherit` / `enabled` / `disabled`）。

`POST` 侧保持兼容：只发旧布尔 `true`、不发三态字段时，服务端会翻译成 `mode=enabled`，与 v3.2.5 的语义逐字节一致。

## 升级方式

| 部署方式 | 操作 |
|---|---|
| Docker | 重新拉取镜像后重建容器（本版没有改动 entrypoint 与 Dockerfile） |
| Magisk 模块 | 面板内一键更新即可（本版**没有改动模块外壳脚本，不需要重刷 ZIP**） |
| 裸机 / Windows | 面板内一键更新，或下载新版二进制替换 |

**升级后值得看一眼的地方**：任务的定时规则那一行多了「可视化编辑」按钮；订阅编辑弹窗里两个自动开关变成了三档；依赖管理页工具条菜单里多了「系统命令行」。
