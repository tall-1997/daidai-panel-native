## 版本概览

`v3.1.1` 是一个**补丁版**，只做一件事：修掉 Watchtower 托管更新在老版本 Watchtower 上**静默失败**的问题。

- [#108](https://github.com/linzixuanzz/daidai-panel/issues/108)（1 条）：按 README 的部署配置改完后，面板更新一直失败，报 `dial tcp 172.20.0.2:8080: connect: connection refused`。

**取证结论要先说清楚：这是我们文档的疏漏，不是用户配错了。** 报告者的 compose 是照着 README 一个字不差抄的——问题出在我们从 `v3.0.0` 起换用了一个**只有新版本 Watchtower 才认识**的环境变量，却**从未在任何地方声明过最低版本要求**。老版本遇到不认识的环境变量是静默忽略的，于是容器正常启动、日志一声不吭，API 端口却从头到尾没开。

本版对现有用户**没有行为变更**：只是把报错换成能照着做的自诊断、给 `ddp check` 补上真探活、并在文档与参考配置里补齐最低版本要求。**已经踩坑的用户不必等升级面板**，见升级须知。本版**没有** APP 侧改动。

感谢 [@backdreamliu](https://github.com/backdreamliu) 提的 issue，以及那句关键线索——「用原来的部署代码正常，按新的改完就不行」。正是这句话把排查范围从网络、防火墙、鉴权一次性收敛到了参考配置本身。

## 升级须知

### 已经踩到这个坑的用户，不必等升级面板

如果你现在点更新就报 `connection refused`，**直接在宿主机上跑这两条就能立刻解决**，与面板版本无关：

```bash
docker compose pull watchtower
docker compose up -d watchtower
```

本版的改动是让这个问题**能被自己发现**（报错说人话、`ddp check` 会提前报红、文档写明最低版本），**而不是替用户去拉镜像**——面板容器刻意不挂 `docker.sock`，物理上也做不到。

> 走国内镜像加速站的话留意一点：加速站上的 `latest` 可能是陈旧缓存，`pull` 完仍是老版本。这种情况改拉具体版本号即可。

## 修复：Watchtower 托管更新静默失败，面板只抛一句 connection refused（#108）

用户报的现象是：按 README 的新部署配置改完之后，面板里一点「检查系统更新」就失败：

```
调用 Watchtower 更新接口失败: Post "http://watchtower:8080/v1/update?...":
dial tcp 172.20.0.2:8080: connect: connection refused
```

> **根因：我们在 `v3.0.0` 换用了一个 Watchtower `v1.20.0` 才引入的环境变量，而且从未声明过最低版本要求。**

**时间线**

| 时间 | 发生了什么 |
|---|---|
| 2026-07-21 | Watchtower `v1.20.0` 发布，**首次**引入 `http-api-endpoints`。`v1.19.0` 及更早的 `internal/flags/flags.go` 里**只有 `http-api-update`** |
| 2026-08-04 | 面板 `v3.0.0`（`db34455`）把参考 compose 里的 `- --http-api-update` 换成了 `WATCHTOWER_HTTP_API_ENDPOINTS: update` |

也就是说，**新写法可用仅两周**我们就切了过去，而且没有在 README、compose 注释、`.env` 示例里的任何一处写下「需要 `v1.20.0`+」。

关键在于老版本的失败形态：**Watchtower 遇到不认识的环境变量是静默忽略的。** 容器照常启动、健康、日志里一个字的报错都没有，**但 HTTP API 的 8080 端口从头到尾不会打开**。所以从用户视角看，这是一台「一切正常、就是更新点不动」的机器。

**第二个因素把这个坑放大了一圈**：参考配置给 Watchtower 自己打了 `com.centurylinklabs.watchtower.enable=false`（避免它把自己也纳入托管），**所以它不会自我更新**——本地那份 `latest` 镜像是哪天拉的，就一直停在哪天的版本。**凡是在 `v1.20.0` 之前部署过的用户，升级面板并按新文档改完 compose 之后，全都会中招。**

而面板当时只是把底层的 `connection refused` 原样往上抛。**用户拿着这句话完全无从自查**：它长得像网络不通、像防火墙、像服务没起来，唯独不像「你的 Watchtower 太老，认不得这个环境变量」。

### 这一版的改法

| | 改动 |
|---|---|
| 面板报错 | 连接层失败时不再抛裸错误，换成带判定结论 + 自查步骤的诊断文案 |
| `ddp check` | 「更新托管」从只看配置改成真探活（见下一节） |
| 文档与参考配置 | README、`docker-compose.watchtower.prod.yml`、`.env.watchtower.prod.example` 全部补上最低版本要求 |
| preflight | 对 compose 的检查补上正向断言 |
| 前端 | 更新弹窗的错误区块支持多行显示 |

**新的报错会把这几件事一次说完**：这个地址解析不到或端口没人监听、更新请求根本没发出去（不是更新本身失败）；最可能的原因是 Watchtower 低于 `v1.20.0`；第二个原因是它不会自我更新、本地镜像可能很旧；然后给出两条可以直接复制执行的命令——先 `docker compose logs <服务名>` 看启动日志里打印的版本号，再 `docker compose pull <服务名> && docker compose up -d <服务名>`。**原始错误原文仍然保留在最后一行**，不做任何吞掉。

**判定「连不上」用的是错误类型，不是字符串匹配。** 走 `errors.As` 认三类：`*net.DNSError`（域名解析不了）、`*net.OpError` 且 `Op == "dial"`（拨号阶段失败）、以及兜底的整体超时。

> 刻意不用文案匹配：`connection refused` 这类文本在不同系统、不同语言环境下都不一样，靠 `strings.Contains` 必然漏判。
>
> 而且只认**拨号阶段**是有意的——连上之后的读写错误不算，那说明 API 其实在监听，属于另一类问题，套这份诊断只会把人带偏。

**命令里的服务名是从 `WATCHTOWER_HTTP_API_URL` 的 host 推导出来的，没有写死。** 用户的服务不一定叫 `watchtower`，给一条抄了会报「no such service」的命令比不给还糟。host 是 `localhost` 或 `host.docker.internal` 这类推不出服务名的值时，退回占位符 `<你的 watchtower 服务名>`，不硬猜。

**「服务端返回非 2xx」是另一类失败，文案一个字没动。** 例如令牌不对拿到 401——那说明 API 明明在监听，端口、网络、版本都没问题，套「你的 Watchtower 太老」的诊断纯属误导。

**顺带修的前端一处**：诊断文案是分行的编号步骤，但更新弹窗的错误区块没设 `white-space`，`\n` 会被 HTML 折叠成空格，**编号步骤全挤成一行，没法照着做**。补上 `pre-wrap` 之后正常换行。

**文档侧补的内容**（三处口径一致）：需要 Watchtower `v1.20.0`（2026-07-21）或更新的版本；说明老版本会静默忽略这个环境变量、端口不开且日志不报错；说明 Watchtower 不会自我更新、老部署升级后需要手动 `docker compose pull watchtower` 再重建；以及国内镜像加速站的 `latest` 可能是陈旧缓存，必要时改拉具体版本。`docker run` 那份写法同样补了——它连 `--pull=always` 都没有，宿主机上早就存在旧镜像时会直接复用。

**preflight 补的那条正向断言值得单独说一句。** 之前对参考 compose 的检查是**单向**的：只断言「不得含已废弃的 `--http-api-update`」。这意味着谁要是误删了 `WATCHTOWER_HTTP_API_ENDPOINTS` 那一行，preflight **全绿放行**，而线上表现恰好就是本 issue 的形态。现在补上「必须含」这一侧，两条断言分开写、各自给各自的失败文案——原来合并成一个 `-or` 的写法就算触发了，读到的也是一句「deprecated flag」，与真实原因南辕北辙。

> 匹配用的是「非注释行 + 子串」，不是裸 `Contains`：compose 里现在写了最低版本说明注释，正文必然提到 `WATCHTOWER_HTTP_API_ENDPOINTS` 和 `--http-api-update` 这两个名字——用裸 `Contains` 的话，正向检查会被注释喂饱（删掉真配置也全绿），负向检查会被注释误伤（没人用那个 flag 也报红）。

## 修复：`ddp check` 的「更新托管」报 OK，但更新其实根本连不上（#108）

这一条是上面那个坑的**帮凶**，值得单独点名。

> **根因：`ddp check` 只检查配置齐不齐，齐了就报 OK——而本 issue 恰恰是「配置完全齐全，但 API 根本没在监听」。**

也就是说，中招的用户即使跑了 `ddp check`，拿到的也是一条绿色的「更新托管 OK」。**这是标准的假阳性**：诊断命令给了一个虚假的安心，用户要一直等到真的去点更新才会发现不对。

**现在会真连一次**：3 秒超时，拿到**任何** HTTP 响应就算通过（含 401 / 404），连不上则报 FAIL，并给出与面板一键更新**同一份**诊断文案。

> 401 和 404 算通过是刻意的：探活要回答的问题是「端口上有没有服务在应答」，不是「鉴权对不对」。能给出 HTTP 响应就说明 API 已经在监听，本 issue 的病根就排除了。所以探活请求**不带令牌**。

**探活打的是 API 根路径，不是 `/v1/update`——这一点必须写清楚。** Watchtower 的 update handler **不校验 HTTP method**，所以拿 `GET /v1/update` 去探活会**真的触发一次更新**。一条本该只读的诊断命令把线上容器重建了，比假阳性严重得多。

两处的文案共用同一个生成函数，避免各写各的然后慢慢漂移。探活失败只让这一条转红，不影响 `ddp check` 的其余检查项。

| 裸机 / Windows | 面板内一键更新，或下载新版二进制替换 |
