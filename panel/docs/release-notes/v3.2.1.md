## 版本概览

`v3.2.1` 以**修复**为主，顺带把定时任务页的两个排序功能一起做了。本版共处理 **6 项 issue 诉求 + 1 条用户直接反馈 + 4 个排查途中顺手修掉的缺陷**：

- [#111](https://github.com/linzixuanzz/daidai-panel/issues/111)（1 条）：面板开代理后，Python 脚本调 `notify.py` 推送报 `HTTP Error 502: Bad Gateway`；关掉代理就正常，JS 版 `sendNotify.js` 完全不受影响。
- [#112](https://github.com/linzixuanzz/daidai-panel/issues/112)（1 条）：全量「备份」导出的定时任务丢了标签，而定时任务页单独「导出」的 JSON 里标签是好的。
- [#113](https://github.com/linzixuanzz/daidai-panel/issues/113)（3 条）：定时任务自定义拖拽排序；「最后运行 / 下次运行」两列点击排序；Node 脚本末尾汇总输出丢失。
- 用户直接反馈（1 条）：依赖管理的小红点**访问过页面也不消除**，而且角标上那个数字在页面里根本找不到对应物。

另外还带上了 v3.2.0 发布之后、本版之前已经进主干的两笔改动：日志详情接口下发 `command` 字段并补齐任务视图的接口文档，以及修好「GitHub Release 标题里的摘要从来没生效过」。

本版有**三处必须先看的变更**（备份包里多了明文 Git 令牌、依赖 / 订阅角标的语义变了、老备份恢复后标签仍然是空的），见升级须知。
本版**没有**改动 Magisk 模块外壳脚本，**不需要重刷 ZIP**；也没有改动 Docker entrypoint 与 Dockerfile。

感谢 [@wanghlstar](https://github.com/wanghlstar) 提的 #111 —— 那份 issue 把完整 traceback、`DAIDAI_NOTIFY_*` 三个变量的实际值、可信代理 CIDR 配置、以及「js 没问题」这条对照全贴齐了。**「JS 版没事」这一句是本次定位的关键**：它一句话就把嫌疑从面板服务端排除、指向了「Python 读代理环境变量而 Node 核心不读」。

## 升级须知

### 1. 备份包里现在会包含订阅的 Git 访问令牌（明文）

修 #112 时顺带修掉了同一机制导致的第二处丢失：**订阅的 `AuthToken`（Git PAT / 私有仓库访问令牌）此前也不会进备份包**，所以从备份恢复出来的 token 型 Git 订阅会失去鉴权、同步直接失败。本版把它补进备份了。

代价必须说清楚：

> **从本版起，备份文件里含有订阅的 Git 访问令牌明文。备份文件请勿外发、勿上传公开网盘、勿贴进 issue。**

如果你的备份需要交给别人、或者放在不完全可信的存储上，**请在创建备份时填写「备份密码」** —— 填了密码的备份会加密导出为 `.enc`，不填则是明文 `.tgz`。

### 2. 依赖 / 订阅的失败角标改成「未读的新增失败」

这两个角标以前数的是**当前失败总数**：只要环境里还有坏的依赖，红点就一直在。本版给它们补上了执行日志那套已读水位 —— **进过对应页面就算看过了，角标归零，之后只报新增的部分**。

也就是说：升级后你进一次依赖管理，侧栏就不再红了，**哪怕失败的依赖还没修好**。想知道还剩几个坏的，看依赖页三个类型页签上的失败数（本版新加，见下文）。详细规则与取舍见「修复：依赖 / 订阅的失败角标」一节。

### 3. 老备份文件里本来就没有标签，恢复它们仍然是空的

这一条容易被误当成「修复没生效」，所以单独写出来：

> **本版修的是「导出时不再丢标签」。已经存在的老备份文件，标签在导出那一刻就已经不在文件里了，恢复时面板无从凭空造出来。**

| 备份文件 | 恢复后任务标签 |
|---|---|
| **本版之后**新建的备份 | 标签完整还原 |
| 本版之前的老备份 | **仍然是空的** —— 这是历史数据缺失，不是修复无效 |

老备份恢复本身不会报错（缺这个键就按空标签处理，与升级前逐字节一致）。想让标签回来，请在升级后**重新做一次备份**。

另外，恢复时 `subscription:<订阅ID>` 这类订阅标签会按新旧订阅主键**重新映射**；如果备份里没有对应的订阅（比如只勾了任务没勾订阅），这条标签会被**丢弃**而不是原样写回 —— 原因见下文 #112 一节，这是刻意的。

## 修复：开代理后 Python 脚本推送报 502（#111）

用户在系统设置里配了代理之后，Python 脚本里 `from notify import send` 一发推送就是：

```
urllib.error.HTTPError: HTTP Error 502: Bad Gateway
RuntimeError: 通知发送失败: HTTP 502:
```

关掉代理立刻正常，同一台面板上 JS 版 `sendNotify.js` 从头到尾没事。

### 根因：面板注入了 6 个代理变量，却从来没设过 `NO_PROXY`

面板一旦配了代理地址，就会往脚本进程注入 `HTTP_PROXY` / `HTTPS_PROXY` / `ALL_PROXY` 及其三个小写版本 —— 这是为了让脚本里的 `pip` / `npm` / `git` / `apt` 能走代理，本身没问题。

问题是**从来没有一起注入 `NO_PROXY`**。而 Python 的 `urllib` / `requests` 默认就认这批变量，于是连发往 `DAIDAI_NOTIFY_URL`（`http://127.0.0.1:<面板端口>/api/v1/notifications/send`，报告者环境里是 5701）的**回调面板自身**的请求也被交给了代理。代理去连**它自己那一侧**的 `127.0.0.1:5701`，那里什么都没有，于是回一个 502。

**所以这个 502 是代理返回的，不是面板返回的。** 用户报的 traceback 里那句 `HTTP Error 502` 停在 `urllib/request.py` 里，正是这个形态。

**JS 版为什么没事**：Node 核心的 `http` / `https` 模块**从不读 `HTTP_PROXY` 环境变量**（要走代理得显式挂 dispatcher 或 proxy-agent）。所以它天然直连，一次都没被劫持过。

### 关于「可信代理 CIDR」，两点都要说清楚

1. **那是另一个功能。** 「可信代理 CIDR」是面板用来判断反向代理来源 IP、取真实客户端 IP 的，跟出站请求走不走代理毫无关系，填多少条都不会影响这里。
2. **就算它是 `no_proxy`，CIDR 写法 Python 也不认。** CPython 的 `proxy_bypass_environment()` 只做「主机名 / IP 全等」与「`.` 后缀结尾」两种匹配，`127.0.0.1/32`、`10.0.0.0/8` 这类网段一律匹配不上。**用户转述的这条判断是对的**，我们实测复核过（见下表第 3 行）。

### 实测：起假面板 + 假代理，8 组对照

假「面板」监听 `127.0.0.1:5701` 返回 200，假「代理」监听 `127.0.0.1:7890` 一律返回 502，子进程里按面板的实现原样注入代理变量，再 `urlopen` 面板地址：

| 场景 | 结果 | 结论 |
|---|---|---|
| 不设代理 | `200 PANEL` | 直连，等于用户「关代理正常」 |
| **面板现状**：6 个代理变量、无 `NO_PROXY` | `502 PROXY-502` | **完整复现用户症状，根因坐实** |
| `no_proxy` 写成 CIDR（`127.0.0.1/32`） | `502` | **CIDR 写法确实无效** |
| `no_proxy=localhost,127.0.0.1,::1` | `200 PANEL` | 第一层修复有效 |
| 只设大写 `NO_PROXY` | `200` | 大写认 |
| 只设小写 `no_proxy` | `200` | 小写也认 |
| `no_proxy=*` | `200` | 全绕过也有效，但不该这么干 |
| 6 个代理变量 + `ProxyHandler({})` | `200 PANEL` | 第二层兜底有效 |

顺带确认了一点：`no_proxy` 里**不需要写端口**，`127.0.0.1` 就能匹配上 `http://127.0.0.1:5701/...`。

### 这一版的改法：三层，且是「合并」不是「覆盖」

| 层 | 做了什么 | 为什么这一层不能省 |
|---|---|---|
| 主修 | 任务运行环境里注入 `NO_PROXY` / `no_proxy`（大小写同值两份） | 环境变量在子进程里是**最后落地**的，只写进程环境会被用户的同名变量盖回去 |
| 兜底 | 代理变量注入函数里再补一份，只补不覆盖，且放在「没配代理就早退」**之前** | 兜住 `env.sh` 导出预算被撑满、`NO_PROXY` 退化成「只赋值、不 export」的静默失效路径 |
| 脚本侧 | `notify.py` 目标是回环地址时，用空 `ProxyHandler` 强制直连 | 用户完全可以在「环境变量」页面自己覆盖 `NO_PROXY`，这层是最后一道保险 |

因为兜底层放在「没配代理就早退」之前，所以**即使你没有配置代理**，脚本进程里也会有一个 `NO_PROXY=localhost,127.0.0.1,::1`。这是刻意的：避免开关代理时脚本行为跳变。

**注入语义是「合并追加」，不是覆盖** —— 这是三种注入策略里的第三种，和另外两种都不一样：

| 策略 | 谁赢 | 例子 |
|---|---|---|
| 保留名 | **面板赢**，你的同名变量被覆盖 | `DAIDAI_*`、`TZ` |
| 只补不覆盖 | **你赢**，你设了面板就不再注入 | `QL_*` 青龙兼容变量 |
| **合并追加** | **两边都保留** | `NO_PROXY` / `no_proxy` |

具体做法：把你写的值按 `,` 切开，只把还缺的 `localhost` / `127.0.0.1` / `::1` 追加到末尾，已经有的不重复加（大小写、前后空格都算「已经有」），**你自己配的白名单一条都不会少**。大小写两个键的已有值都会被吃进同一个集合再一起写回，所以「只写了小写 `no_proxy`」也不会被静默丢掉。

**`pip` / `npm` / `git` / `apt` 继续走代理，完全不受影响** —— 白名单里只有三个回环主机名。

### 其余配套

- `notify.py` 只对**回环地址**豁免代理。它支持 `url=` 覆盖成外网地址，那条路径仍然走默认 opener，没有被打断。
- 前置脚本 / 钩子里回传 `NO_PROXY`（或小写）时，走「**放行但提示**」：告诉你覆盖后可能出现「脚本回调面板自身被代理接管、报 HTTP 502」，并提示用追加写法（`export NO_PROXY="$NO_PROXY,..."`）而不是整体赋值。
- 「系统设置 → 代理设置」的说明弹窗补了一句：面板会自动为 `localhost` / `127.0.0.1` / `::1` 放行直连；你设的 `NO_PROXY` 会与它们合并（你的值不会被覆盖，但也无法把这三条移除）。
- `docs/script-api.md` 的注入变量表补了 `NO_PROXY` / `no_proxy` 一行，并把三种注入策略的区别写成了对照表。

## 修复：全量备份丢掉定时任务标签，顺带丢了订阅的 Git 令牌（#112）

用户报的现象很干净：备份说明里明明写了包含标签，但备份包里的定时任务没有标签，而定时任务页单独「导出」的 JSON 有。

### 根因：一个 `json:"-"`，只在「过 JSON」的那条路径上发作

任务的标签字段在模型上标了 `json:"-"`，而备份清单直接把整表的任务对象扔进去序列化 —— 于是整列标签在写 JSON 那一刻被丢掉。

这也解释了另外两条路径为什么是好的：

| 路径 | 标签 | 为什么 |
|---|---|---|
| 定时任务页「导出」 | 一直是好的 | 它自己按字段拼一份 map（`labels` 取的是 `GetLabels()`），不经过模型的 JSON 序列化 |
| 青龙导入 | 一直是好的 | 清单在内存里直接交给恢复流程，根本不落 JSON |
| **全量备份** | 丢 | 直接序列化模型对象 |

### 顺带修了同机制的第二处：订阅的 `AuthToken`

按同一个特征把备份结构整个查了一遍，发现**丢的不只标签一处**：订阅的 `AuthToken` 也是 `json:"-"`，同样一个字节都没进备份包。后果比丢标签更实际 —— 从备份恢复出来的 token 型 Git 订阅**会失去鉴权**，同步直接失败，而用户很难把这件事和「恢复过一次备份」联系起来。

代价见上面的**升级须知第 1 条**：PAT 从此以明文进入备份包。

### 加了一条反射护栏测试，堵住「以后又静默丢一个字段」

这次是靠用户报了才发现的，而这类丢失**没有任何报错**。所以补了一条用反射遍历的守卫用例，钉死这个不变量：

> 备份清单里凡是直接放或嵌入模型对象的地方，该模型**不得存在未被外层覆盖的 `json:"-"` 字段**。

以后谁再给模型加一个 `json:"-"` 字段，测试当场变红，不用等下一个用户来报。

### 恢复时订阅标签必须重映射 —— 不做的话比原 bug 更糟

这一条是「修复反而更危险」的坑，必须写出来。

恢复流程会给订阅**重新分配主键**（旧 ID 不会被复用）。如果把 `subscription:<旧ID>` 原样写回，这条标签就可能挂到**另一个不相干的订阅**头上；而订阅同步里有一条 autoDelete 分支，会对「认领到、但不在本次候选集里」的任务执行**物理删除**（连任务带日志一起）。

所以规则定成这样：

1. 能在「旧订阅 ID → 新订阅 ID」映射里命中 → 改写成新 ID；
2. **没命中**（订阅没被一起恢复、或备份里就没有那个订阅）→ **丢弃这条 `subscription:` 标签**，绝不保留旧 ID；
3. 分组标签、用户自定义标签**一律原样保留**。

「只勾选任务、不勾选订阅」时映射为空，所有 `subscription:` 标签会被丢弃 —— 这与升级前的行为等价（升级前压根就没有标签）。

## 新增：定时任务支持自定义拖拽排序（#113-1）

任务列表左侧多了一列拖拽手柄，按住就能把任务拖到你想要的位置，**顺序会持久化**，刷新页面、换设备打开都还在。

### 关键的安全决定：另开一列，绝不复用 `sort_order`

任务表上本来就有一个 `sort_order`，看起来正好能拿来用 —— **但它是「开机自启任务的执行顺序」契约**，调度器按它决定开机时谁先跑谁后跑。拿它做列表拖拽，等于用户每拖一次列表就在**静默改写自己的开机编排**，而且现有那条守着开机顺序的闸门测试因为自己显式设值，**根本抓不到**这个回归。

所以本版新开了一列 `list_order` 专门存展示顺序：

- **升级后你的任务列表顺序逐字节不变** —— 存量行落 0，整体行为与升级前完全一致，直到你第一次拖动。
- 数据库补列走既有方式，老库自动平滑升级，有迁移测试守着（含「跑第二次仍然幂等」）。
- **拖拽只写 `list_order`，一个字节都不碰 `sort_order`** —— 这是本项改动最关键的性质，浏览器实测专门量过（见下）。

### 规则：只能同区互拖，跨区会被拦下

拖拽只允许在「**置顶状态相同 + 状态分组相同**」的一桶之内进行。把普通任务拖到置顶任务之前，会直接被服务端拒绝：

```
置顶任务与普通任务、启用与禁用任务请分别排序，跨区移动请用置顶 / 启用按钮
```

**落点是相对整个区算的，不是相对当前页**：服务端取兄弟任务时从数据库拿整桶（不分页），一次拖动把整桶按 10 的步长重新编号。所以在第几页上拖都行，跨页之间的相对顺序不会互相打架。（列表本身是服务端分页的，一次只渲染当前页，所以没法把第 2 页的行直接拖到第 1 页去 —— 要跨页调位置，先把每页条数调大。）

### 什么时候拖不动（都有 tooltip 说明原因）

手柄会置灰而不是消失，鼠标停上去会告诉你为什么：

| 情况 | 提示 |
|---|---|
| 正在按列排序 | 当前正在按列排序，先切回「默认排序」再拖拽 |
| 当前视图自带排序规则 | 当前视图自带排序规则，切到不带排序的视图再拖拽 |
| 列表只有一条任务 | 至少两条任务才能拖拽排序 |
| 账号没有操作权限 | 当前账号没有排序任务权限（观察者角色连拖拽列都不渲染） |

前两条是必须的：展示顺序既然由排序字段决定，拖出来的位置刷新就会被排序规则覆盖回去，与其让人「拖了个寂寞」，不如直接禁掉并说清楚。

**两个边界写在前面**：拖拽排序目前**只做了桌面表格**，移动端渲染的是卡片列表、没有表格，这一版不支持；另外任务页有 3 秒一轮的状态轮询，会整体替换列表数据 —— 拖拽期间轮询会自动暂停，否则正在拖的那一行会连 DOM 一起被换掉、拖拽当场断在半空。

## 新增：「最后运行 / 下次运行」两列点击排序（#113-2）

点表头就能排，第三次点取消该列排序、回落默认排序（置顶 → 状态 → 你拖出来的顺序）。

- 「下次运行」不是数据库里的列，是响应时按 cron 现算的快照，所以这一列的排序在内存里完成。
- **空值语义（两列一致）**：从未运行的任务、已禁用或非 cron 而没有下次运行的任务，**恒排在最后，不随升序 / 降序翻转**。判定写在方向翻转之前，所以你点几次它都在底下 —— 这正是「想看接下来哪些脚本即将运行」时最需要的行为：不会有一堆「从未运行」把真正快要跑的任务挤下去。
- 窄桌面（<1600px）下「最后运行」整列是隐藏的，**工具栏的排序下拉里补了对应选项**作为替代入口，否则那档视口下根本点不到这个排序。
- 表头箭头与实际排序始终一致：切到其它排序时箭头会一起收回去，不会出现「表头指着最后运行、实际按别的规则排」。

### 验证到什么程度

前端仓库**没有自动化测试**（无 vitest、无 test 脚本），所以这两项只能人工实测。本轮起了独立面板实例 + 独立 profile 的 Chrome，造 6 条任务逐项量过：

- **列排序**：下次运行升序 A(01:52) → C(02:00) → B(03:00) → D(05:00) → E(06:00)，手动任务 F（无下次运行）垫底；**降序时 F 仍然垫底** —— 空值不随方向翻转，契约成立。
- **拖拽**：把第 6 行拖到第 3 位成功，`list_order` 落库为 10/20/30/40/50/60，而 **`sort_order` 全部仍为 0** —— 开机任务的执行顺序完全没被动到。
- **持久化**：刷新页面后顺序完整保持。
- **跨区拦截**：把未置顶任务拖到已置顶任务之前 → 400 + 上面那句提示，且**六条任务的 `list_order` 一个都没变**（不是「先改了再报错」）。
- **与列排序互斥**：列排序生效时 6 个拖拽手柄全部置灰，取消排序后全部恢复。

**未验证**：移动端（本版本就不支持拖拽）、跨页拖拽、真实 Docker 容器与 Magisk 设备上的端到端。

## 说明 + 新工具：Node 脚本尾部输出丢失（#113-3）

报告者说「日志末尾只剩汇总的第一行分隔线，后面的执行完成汇总 / 有效账号 / 任务统计 / 中奖列表全没了，但面板自己的『执行结束』行正常」，并且自己 clone 源码归因为「Node 管道模式 stdout 异步写 + 脚本立即退出，缓冲被丢」。

### 结论先说：归因成立，但条件更窄 —— 元凶是脚本末尾的 `process.exit()`

面板侧的持久化链路整条查下来**没有丢数据点**，两道大小上限超限时**都会在日志里留下可见标记**（见下）。真正的丢失发生在子进程自己的用户态缓冲里 —— 进程已经没了，面板再怎么等也拿不到。（所以报告者建议里那条「面板在追加『执行结束』行前等 100ms」是无效的：数据在进程消失的那一刻就不存在了，不是还在路上。）

实测数字（WSL Linux + node 18.19.1，1.77 MB 输出，每档 **40 轮**）：

| 退出方式 | 丢尾巴 | 最严重的一次 |
|---|---|---|
| 自然退出（不调 `process.exit`） | **0 / 40** | — |
| **末尾 `process.exit(0)`** | **5 / 40（12.5%）** | 只收到 69403 / 1770453 字节，**丢了 96%** |
| 退出前 `await globalThis.daidaiFlush?.()` | **0 / 40** | — |

三点值得单独指出：

1. 它是**概率性**的（12.5%），同一个脚本大多数时候正常、偶尔丢一大截，非常容易被误判成「面板偶发 bug」。
2. 丢失量**不限于尾巴** —— 最坏那次连前面 96% 的日志一起没了。
3. 第一轮我们在 Windows 与 Linux 上各跑 12 组、全都没复现出来，那是**样本太少的假阴性**；加到每档 40 轮结论才翻转。这也是为什么这类问题很难靠「我试了几次都好的」来排除。

### 给脚本作者的三条

**① 末尾调 `process.exit()` 的话，先把 stdout 刷干净：**

```js
await globalThis.daidaiFlush?.();   // 等 stdout 真正写完
process.exit(0);
```

这个函数就是照报告者第 3 条建议加的。写 `?.()` 而不是 `()`，这样脚本在面板之外（本地、青龙）跑时不会因为没有这个函数而报错 —— 和 `daidaiDone?.()` 是同一个道理。它注入在 Node 预加载脚本正文里，**即使你关掉了「半路静默结束」检测，它也照样存在**。

**② 其实最省事的办法是：别调 `process.exit()`。** 让主流程自然跑完，Node 会自己等写完再退出（上表 0/40）。只有在「还有定时器 / 长连接吊着事件循环、不主动退就一直挂着」时才需要它，那时才配上 `daidaiFlush`。

**③ 不要用 `fs.writeSync(1, ...)` 代替 `console.log`。**

网上（以及这次 issue 里「更彻底：用同步写」那行注释）常见的「直接同步写 fd 1」——**请不要照做，它会打乱输出顺序**。`fs.writeSync` 绕过了 `console.log` 背后那条写队列，直接往 fd 1 插队。我们实测到的现象是：脚本末尾用它打的汇总，被塞进了**前面某一段批量日志的中间**。看起来像「日志错乱」，比丢尾巴更难排查 —— 内容一个字都没少，只是位置不对。

除了 `process.exit()`，还有三种写法也会丢：进程被信号杀掉（OOM / 手动停止 / 外部 `kill`）、`worker_threads` 里 `console.log` 再转发回主线程、自己包了一层「攒够 N 行再输出」的 console 缓冲。

### 怎么判断「是不是被面板截断的」

面板确实有两道上限，但**两道超限都会在日志里留下可见标记**：

| 上限 | 默认值 | 计算范围 | 日志里的标记 |
|---|---|---|---|
| `max_log_content_size`（系统设置 → 任务运行 → 日志内容上限） | `102400000` 字节（≈ 97.66 MiB） | **单次子进程**输出，不是整个任务累计 | `[日志已截断，超过最大大小限制]` |
| 落盘日志文件大小 | 10 MB（写死，不可配） | 单个日志文件 | `[日志文件已达到大小限制，停止写入]` |

**这两行一行都没有，就不是被面板截掉的。**

### 面板侧交付了什么

- 新增 `globalThis.daidaiFlush()`（上面那个，对应报告者的建议 3）。
- **子进程被信号杀掉时补一行可见提示**，不再只留一个「退出码 -1」让人猜：
  `[脚本进程被信号终止：killed(9)（退出码 -1）。常见原因：内存超限被系统 OOM Killer 杀掉、面板或用户手动停止、外部 kill]`
  （超时终止仍然只报「任务超时」那一行，不会两行互相打架；Windows 上不会出现这一行。）
- `docs/script-api.md` 新增「**脚本尾部输出为什么会丢**」小节，把上面这套「先定位 → 再对症 → 最后确认」完整写进去了 —— 这对应报告者的建议 1。
  文档里刻意**不下机理定论**：网上常说「Node 往管道写 stdout 是异步的」，但 Node 官方 “A note on process I/O”
  那张表写的是 pipes 在 Windows 与 Linux 上同步、只有 macOS 异步，与上面这组实测对不上。
  与其押一个说不圆的机理，不如只给可复现的规则：**调了 `process.exit()` 就先 flush**。

## 修复：依赖 / 订阅的失败角标进页面不消除，且数字与页面对不上（用户反馈）

用户反馈：「依赖管理这里一直会显示小红点，即使我访问了页面之后，也不会消除。」截图里侧栏角标是 **9**，而依赖页 Node.js 标签下写的是「全部 8 / 已安装 6 / **失败 2**」。

这里其实是**两个问题**，用户只提了第一个。

### 问题 1：三个失败角标里，只有「执行日志」有已读机制

- `/logs`（执行日志）有完整的**已读水位**：进页面即标记已读、角标归零，当天再出现新失败仍然会提醒。
- **`/deps` 与 `/subscriptions` 完全没有这套东西** —— 它们直接用后端返回的实时失败计数，语义是「你环境里还有 N 个坏的」，只有把失败依赖修好或删掉才会消。

所以用户看到的行为是当前设计的必然结果，但它**与执行日志的行为不一致**，也不符合预期。本版给这两个补上同一套水位（这是升级须知第 2 条那处变更），四条约束都照着执行日志那套抄齐了：

| 约束 | 为什么 |
|---|---|
| **水位不按天失效** | 执行日志的存档带日期，是因为它统计的本来就是「今日失败数」、跨天会归零；而依赖 / 订阅的失败是**持久状态**，按天失效会变成「今天消了、明天又亮」，等于没修。所以这两个的水位只按**用户名**隔离，不带日期 |
| **水位必须能降** | 你修好几个之后失败数变小，水位要跟着降，否则得攒够超过历史峰值才会再提醒 |
| **进页面两条路径都要标已读** | 侧栏页面是 keep-alive 缓存的，第二次以后进页面走的是另一个生命周期钩子，只写一处会**只有首次访问生效** |
| **首屏数据没到时要能补记** | 直接刷新停在依赖页时，页面初始化早于角标数据首发，此刻计数还是 0，按 0 记水位等于没记 —— 用挂起补记解决 |

顺带修了一处连带问题：依赖页「安装中」的提示原来挂在失败总数的分支上，标记已读之后那条分支虽然渲染不出任何东西、却仍然占着位置，会把「安装中」的提示一起吃掉；现在改挂在未读数上。

### 问题 2：角标那个数字，在页面上根本找不到对应物

- 侧栏角标数的是**全表** `status='failed'`，**跨 Node.js / Python / Linux 三个类型、跨所有 Python 版本**（截图里的 9）。
- 依赖页的「失败 N」只数当前列表，而当前列表只有**当前选中类型**（Python 还只有当前版本）—— 截图里 Node.js 的 2。

于是那个 9 在页面上任何地方都找不到，用户得挨个切三个标签才能凑出来。

本版给 `GET /deps` 增加了一个跨类型的失败数汇总（一条 `GROUP BY`，`nodejs` / `python` / `linux` 三个键恒存在），**依赖页三个类型页签上各挂一个失败数**，鼠标停上去有说明。Python 那个**刻意跨所有 Python 版本统计** —— 只有三者之和恰好等于全表失败数，页签上的数字才能和侧栏角标对上账（页签 title 里写了这一点）。

选这条而不是让前端并发拉三次、也不是读角标数据：依赖页本来就在 3 秒轮询这个接口，计数天然新鲜且**零额外请求**。另外这个汇总在请求失败时刻意不清零 —— 网络抖一下就把「有 3 个失败」抹掉，比不显示更糟。

### 验证到什么程度

起了独立面板实例 + 独立 profile 的 Chrome，直接造 **nodejs 2 / python 5 / linux 2 = 9 条失败依赖 + 1 条失败订阅**（与用户截图同形），浏览器实测 11 项全过，其中关键的几条：

| 场景 | 结果 |
|---|---|
| 初始状态 | 侧栏「依赖管理 9」「订阅管理 1」，无水位存档 —— **复现用户现象** |
| 进依赖页 | 角标消失，水位落盘为 `{"u":"admin","n":9}` —— **不含日期字段**，「不按天失效」落实 |
| 离开再回来 / F5 停在依赖页 | 角标都不复活 |
| 三个类型页签 | Node.js 2 / Python3 5 / Linux 2，**三者之和 = 9 = 原侧栏角标** |
| 失败数 9 → 11 | 角标显示 **2**（增量），不是 11 |
| 失败数 11 → 5（低于水位） | **水位跟着降到 5**，角标归零；此后再新增 1 条，角标显示 **1**（没有留下「要攒够历史峰值」的后遗症） |
| 换账号登录 | 角标恢复成完整数字，**不继承上一个人的「看过了」** |

一个已知边界：水位按用户名隔离，但同一个浏览器里三个存档各只有一个槽位 —— 换账号并进过页面之后，会覆盖掉上一个账号的水位。多人共用同一台机器同一个浏览器时，最坏是被覆盖的那个人再被提醒一次。

## 顺带修掉的 4 个缺陷（排查 #113-3 时发现）

这四个都是查日志链路时撞见的真实缺陷，与用户报的现象无关，但都会影响实际使用：

### 1. 日志落盘每写一行就 `fsync` 一次，而且持着全局锁

一个输出两万行的脚本 = **两万次串行 `fsync`**，全压在脚本输出的同步路径上；期间**所有并发任务**的日志写入都要排队等这把全局锁，慢盘上能把整个面板拖成龟速。

去掉它是安全的：写入走的是 `write(2)`，数据落地就已经在内核页缓存里，**面板进程 panic、被 kill、容器重启都不会丢**，只有整机断电才可能丢尾巴。任务结束时日志文件会被 Close 落盘，且那一步排在「done 事件」之前，所以前端收到完成事件时文件已经完整关闭，之后去读拿到的内容是全的。`O_APPEND` 与「超限写一次可见标记后停写」的语义都没动。

### 2. SSE 不给裸 `\r` 分帧，标准客户端会静默丢内容

终端进度条用裸 `\r` 回到行首覆盖当前行，这个字符必须一路传到前端。但 **SSE 的线格式里 CR 本身就是行终止符**：`data: 10%\r55%\r100%` 在标准解析器（浏览器原生 `EventSource`、各语言 SSE 客户端）眼里是三行，后两行没有字段名，**会被静默丢弃 —— 连报错都没有**。而打开日志弹窗时这里会被喂进整份历史日志，里面往往有成百上千个裸 `\r`。

改法是**不动字符、只改分帧**：每碰到一个后面还有内容的裸 `\r`，就让它落在当前帧最后一条 data 行的末尾，剩下的内容另起一帧。实测对照：

| | 标准 EventSource | 本仓前端 |
|---|---|---|
| 改动前 | `10%` + 完成 —— **丢了 55% 与 100%** | 逐字节完好 |
| 改动后 | `10%55%100%` + 完成 —— **内容完整** | **逐字节一致**，前端零改动 |

（顺带说明为什么没采用「同一帧里多条 data 行、每条以 `\r` 结尾」这个更直觉的写法：SSE 规定同帧多条 data 行用 `\n` 拼接，那样裸 `\r` 会变成 `\r\n`，前端把它当真实换行，进度条会从「原地刷新」变成**多行刷屏** —— 那才是真回归。）

### 3. 实时日志缓冲的切片别名会让内容错乱

实时日志缓冲区在拼接上一段留下的不完整 UTF-8 尾巴时，新旧数据共用了同一块底层数组，会把已经拼好的数据**头部字节直接覆写掉**，表现为日志开头几个字节变成上一段的尾巴。只在「上一次正好切断一个多字节字符」时触发，所以平时看不出来，**中文日志更容易撞上**。改成先分配新数组再拼，对外行为完全不变。

### 4. 多账号并发（`conc`）模式下自生成的行会和下一段输出粘连

`conc` 模式自己生成的行（开始执行 / 执行完成 / 执行错误 / 截断标记）末尾没有换行，在实时日志里会和紧跟其后的脚本输出**粘成一行**；而转发的脚本输出片段本来就带换行，落盘时又会多出一个空行。现在统一成「本来就以换行或裸 `\r` 收尾就不动，否则才补一个 `\n`」，两头都对了，且裸 `\r` 保持原样、进度条语义不受影响。

## 关于 APP

本版**没有** APP 侧改动，APP 不需要跟随升级。

新增的接口字段都是**只增不改**：`PUT /tasks/sort` 是新端点（复用已有的 `tasks` 权限范围，Open API 用户**不需要重新授权**）；任务列表多了 `list_order`、`GET /deps` 多了 `failed_by_type`，APP 不认识就不读，行为与升级前完全一致。（API 文档同步更新，顺带补上了 `GET /deps` 一直漏写的 `python_version` 查询参数。）

**有一处值得 APP 用户看一眼**：日志流的 SSE 分帧改了（见上面「顺带修掉的 4 个缺陷」第 2 条）。用浏览器原生 `EventSource` 的客户端会从「带进度条的日志被静默丢掉一大半」变成**内容完整**；自带解析器的客户端最坏也只是进度条从「原地覆盖刷新」变成「片段直接相接」，**不会丢数据**。本仓前端已确认逐字节一致，独立 APP 仓库那一份**没有实测**，建议自己打开一次带进度条的日志看看。
