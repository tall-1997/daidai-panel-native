# 定时任务不执行 / 没有日志

现象很典型：脚本在「脚本管理 → 调试运行」里跑得好好的，加成定时任务之后到点什么都不发生，点开任务的日志抽屉，只有一句 **「该任务还没有日志记录」**。

这篇文档写给**遇到这个现象的用户**，从上往下一条条过即可，不需要懂面板内部实现。

> 一句话版本：「该任务还没有日志记录」不是「脚本跑失败了」，而是**这次执行压根没开始**。
> 所以往脚本里加 `print`、改 shebang、换 Python 版本，一律不会有任何变化 —— 要查的是**调度**这一侧。

## 0. 先看懂那句「该任务还没有日志记录」

**在哪里看**：任务列表 → 目标任务那一行 → 点「日志」，弹出日志查看窗口。

这句提示严格等价于一件事：**面板的日志表里，这个任务一行记录都没有。**

而任务日志是**执行器起进程的那一刻就建好的** —— 只要脚本真被拉起来过，哪怕它第一行就语法错误、哪怕解释器压根不存在，都会留下一条失败日志。所以「一行都没有」只可能意味着：

> 这次执行**从来没有被调度器交给执行器**。

由此得到两条结论：

1. **脚本本身、依赖、Python / Node 版本都不是原因。** 它们要等执行器起了进程之后才有机会出问题。
2. 能走到这个结果的路径一共 **6 条**，而它们在面板上**长得一模一样** —— 任务都显示「已启用」，「下次运行」列也都有一个像模像样的时间。

所以只能按顺序一条条排除。下面 6 步就是这 6 条路径，每一步都写清了「在面板哪里看、看到什么算正常、不正常怎么办」，从上往下过一遍即可。

## 1. 看「定时规则」列

**在哪里看**：任务列表的「定时规则」列（手机 / 窄屏下在任务卡片里，标签同样叫「定时规则」）。

| 显示的内容 | 什么意思 |
|------|------|
| 一段 cron 表达式，如 `0 30 7 * * *` | ✅ 正常，这是定时任务，会自动触发 |
| **手动运行** | ⚠️ **永远不会自动触发** |
| **开机运行** | ⚠️ 不按时间触发，只在**面板启动时**跑一次 |

「手动运行」和「开机运行」是两种独立的任务类型，它们根本不进 cron 调度 —— 这是设计如此，不是故障。「手动运行」只能靠人点任务行的「运行」按钮（或走接口 `PUT /tasks/<id>/run`）触发。

这两种类型在「下次运行」列会带一个**灰色**信息图标，提示语分别是「该任务类型不会自动触发，只能手动运行」和「该任务只在面板启动时自动执行一次，不按定时规则触发」。**它是灰色的，说明这只是在陈述任务类型、不是故障**；[第 2 步](#2-看下次运行列旁边有没有警示图标)那个是**橙色**警示图标，才是真出问题了。

**怎么办**：编辑任务 → 「基本信息」→ 把「定时类型」改成「常规定时」，并填写「定时规则」，保存。

## 2. 看「下次运行」列旁边有没有警示图标

**在哪里看**：任务列表的「下次运行」列。

把鼠标移到图标上（手机上点一下）看提示语，两句话说的是完全不同的事：

| 看到什么 | 什么意思 |
|------|------|
| 一个具体时间，旁边干干净净 | ✅ 正常 |
| **灰色**信息图标，提示语在说「不会自动触发 / 只在面板启动时执行」 | 这是手动 / 开机运行任务，回[第 1 步](#1-看定时规则列)，不是故障 |
| **橙色**警示图标，提示「**未注册到调度器，重新保存一次任务即可恢复**」 | ⚠️ 本步要处理的就是它 —— 任务没有真正注册到调度器 |

**这个图标在说什么**：「下次运行」显示的时间，是面板拿你的 cron 表达式**现算**出来的 —— 表达式合法就一定算得出来，这跟「这个任务有没有真的被注册进调度器」是两回事。两边对不上时就出这个图标。它对应的正是最让人困惑的那一类：**任务显示「已启用」、有「下次运行」时间，到点却什么都不发生。**

**怎么办**：照提示做就行 —— 打开任务的编辑弹窗，**什么都不用改，直接点保存**。保存会重新注册一次调度，图标随之消失。

## 3. 确认时间是不是还没到

**在哪里看**：还是「下次运行」列，看那个时间到底是几点。

这是最容易被忽略、也最容易自证的一条：从「脚本管理」里选中脚本、点「添加到定时任务」建出来的任务，**预填的定时规则是 `0 0 0 * * *`，也就是每天 00:00**。（在任务页直接点「新建任务」时预填的是「每分钟」，两个入口不一样。）

于是白天用「添加到定时任务」加完，当天不会再跑，**最长要等到第二天零点** —— 中间这十几个小时里，任务确实是「已启用、有下次运行时间、没有任何日志」。

> 从 v3.2.3 起，新建任务成功后会直接告诉你下次运行时间，并给一个「立即运行一次」的按钮，不必再自己算。

**怎么办**：

- **想立刻验证**：点任务行的「运行」按钮手动跑一次。手动运行和定时触发用的是同一个执行器，会正常写任务日志，跑完日志抽屉里立刻就有内容。
- **想改频率**：编辑任务 → 「定时规则」，改成你要的表达式。

> 顺带一个有用的判据：**手动「运行」能跑出日志、到点却依然什么都没有** —— 那就说明脚本和运行环境都没问题，问题出在「有没有注册进调度器」这一侧，回到[第 2 步](#2-看下次运行列旁边有没有警示图标)。

## 4. 看「状态」列是不是停在「运行中」

**在哪里看**：任务列表的「状态」列，取值有「空闲中」「禁用中」「排队中」「运行中」四种。

| 看到什么 | 什么意思 |
|------|------|
| 不跑的时候显示「空闲中」 | ✅ 正常 |
| 长时间停在「**运行中**」 | ⚠️ 上一次执行还没结束（这一行的主操作按钮也会从「运行」变成「停止」） |

**为什么它会挡住后面每一次触发**：任务默认**不允许多实例**，上一次还在跑，后面每次到点触发都会被跳过。而任务的「超时(秒)」**默认是 0，含义是永不超时** —— 一个卡死的脚本（在等一个永不返回的请求、在等一个根本起不来的浏览器）就这么一直占着位置，后面的触发一次都执行不了。

**怎么办**（三选一，也可以组合）：

| 做法 | 在哪里改 | 适合什么情况 |
|------|----------|--------------|
| 先把当前这次终止掉 | 任务行的「停止」按钮 | 应急，先让后续触发恢复 |
| 给任务设一个超时时间 | 编辑任务 → 「高级设置」→ 「超时(秒)」，填 600 之类 | **推荐**。以后卡住会被自动终止、判失败并正常发通知 |
| 打开「允许多实例」 | 编辑任务 → 「高级设置」→ 「允许多实例」 | 只在脚本本身能安全并行时才这么做 |

**从 v3.2.3 起，被跳过会留下记录。** 打开这个任务的**详情**（任务行「运行 / 停止」按钮右边那个下拉箭头 → 「详情」），里面会多出一行 **「最近一次被跳过」**，写着时间和原因：`上一次执行仍在进行中，且该任务未开启「允许多实例」，本次触发没有执行`。

> **为什么记在任务详情里、而不是在日志里加一条**：跳过意味着这次**压根没执行**。给它建一条任务日志的话，它会一并混进仪表板的「已终止」统计和耗时统计；更糟的是它的时间比被它阻塞的那次执行更晚，会顶掉「最近一次日志」—— 你点开日志想看上次跑了什么，看到的却是一句「本次触发被跳过」。记在任务上就没有这些副作用，而且天然只保留最近一次：一个每分钟触发的任务卡上三小时，也不会刷出一百八十条。

## 5. 「上次结果」有值，日志却说没有

**在哪里看**：任务列表的「上次结果」列。

如果这一列明明写着「成功」或「失败」，点开日志却说没有记录 —— 那不是「还没跑过」，是**日志已经被保留策略清掉了**。

面板每 6 小时自动清理一次，把超过保留期的任务日志记录和磁盘上的日志文件一起删掉。保留期在 **设置 → 任务运行 → 「日志删除频率」**（写成「每 N 天」），**默认 7 天**。

「上次结果」不受影响 —— 它存在任务自己那一行上，不跟着日志一起删，所以才会出现「结果还在、日志没了」这种看起来矛盾的组合。

**怎么办**：确认这个任务上次执行是不是已经超过保留期了。是的话属于正常行为；想留久一点就把保留天数调大（最大 3650 天）。

**新版在这种情况下会直接说明日志是被清理的**，而不再笼统地说「还没有日志记录」。

## 6. 翻面板日志

前 5 步都排除掉之后，再去看面板自己的日志。

**在哪里看**：**设置 → 面板日志**（需要管理员账号）。Docker 部署也可以直接 `docker logs daidai-panel`。

在关键词框里搜这三个词：

| 搜什么 | 日志长什么样 | 什么意思 / 怎么办 |
|--------|--------------|-------------------|
| **跳过** | `任务 12 本次触发被跳过：上一次执行仍在进行中……` | 被多实例闸门拦下了，回[第 4 步](#4-看状态列是不是停在运行中) |
| **入队失败** | `任务 12 定时触发入队失败（本次不会执行）: task queue is full` | 触发到了，但没能排进执行队列。队列有 1000 个位置，能塞满说明执行线程长时间被占满 —— 到 **设置 → 任务运行 → 「定时任务并发数」** 调大，同时回[第 4 步](#4-看状态列是不是停在运行中)看看是不是有任务卡住了。冒号后面写的是 `scheduler stopped` 则是面板正在关停，重启后自愈 |
| **注册调度失败** | `任务 12 重新注册调度失败: ……` | 这个任务的定时规则没能注册成功，后面冒号里就是原因。多半是表达式本身有问题，回任务编辑页重填并保存 |

> 「入队失败」这一类**只写面板日志**，任务上没有任何痕迹 —— 队列满是个高频、瞬时的状态。所以第 6 步是这几条路径唯一能看到证据的地方。

## 7. 关于 Playwright / 浏览器自动化脚本

Playwright、Puppeteer、Selenium 这类脚本还有一层额外的坑。下面几条都跟调度无关，是**环境**问题 —— 但它们造成的现象是「任务日志里有一条失败记录」，而不是「没有日志」。如果你的现象是后者，请先走完前面 6 步。

### 面板镜像不预装 Playwright：到「依赖管理 → Linux」一键安装

面板镜像**不预装 Playwright，也不预装 Chromium 及其运行库**（libnss3、libatk、libgbm、字体等一大批系统包），不用浏览器的人不必多背这几百 MB。需要时在面板里一键补齐：

**入口**：依赖管理 → **Linux** 页签 → 说明栏里「安装编译工具链」旁边的「**安装 Playwright 运行环境**」。「新增依赖」旁的下拉菜单里也有同名入口。需要管理员账号。

点下去之后面板做三件事，全部排进同一个安装队列依次执行，进度和日志就在依赖管理页里看：

1. **系统库**：把 Chromium 需要的 26 个系统包（21 个运行库 + 5 个字体相关的包，含中文字体 `fonts-wqy-zenhei`）逐个登记成 Linux 依赖并安装；
2. **Python 包**：在默认 Python 版本下装 `playwright`；
3. **浏览器**：`playwright` 装好后，在同一条依赖记录里接着下载 Chromium，放到数据目录下的 `deps/ms-playwright`（Docker 默认 `/app/Dumb-Panel/deps/ms-playwright`）。

全部装完通常要几分钟，Chromium 本体有一两百 MB。

> **只支持 Debian 12（bookworm）版镜像，且架构是 amd64 或 arm64。** 按钮会先检查当前环境，不满足时置灰并写明原因。Alpine 版镜像为什么不行，见本节后面的[「Alpine 版镜像跑不了浏览器」](#alpine-版镜像跑不了浏览器请用-debian-版)。
>
> 浏览器是从 Playwright 的官方 CDN 下载的，国内网络可能很慢甚至失败。失败时依赖日志会写明「是浏览器下载失败，不是 pip 失败」。两条出路：到 **系统设置 → 代理设置** 填好「代理地址」；或者给容器设置环境变量 `PLAYWRIGHT_DOWNLOAD_HOST`，指向可用的下载镜像。然后再点一次一键安装即可。

### 容器重建 / Watchtower 更新之后

一键安装装下的三样东西，重建容器后的去向不一样，但都不需要你再动手：

| 装了什么 | 放在哪 | 重建容器后 |
|----------|--------|-----------|
| Chromium 浏览器 | 数据目录下的 `deps/ms-playwright` | 在数据卷里，**不丢** |
| Python 的 `playwright` 包 | 数据目录下的托管 venv（`deps/python/<版本>`） | 在数据卷里，**不丢** |
| 26 个系统库 | 容器的系统目录 | 随旧容器一起丢，但它们已经登记成 Linux 依赖，**面板启动校验会在后台自动重装** |

所以刚重建完的几分钟里，Playwright 脚本可能报缺系统库（`error while loading shared libraries`、`Host system is missing dependencies`）—— 这是后台还在重装。到 **依赖管理 → Linux** 看进度，全部变成「已安装」后再跑即可；任务日志里碰上这类报错，面板也会在提示里写明正在后台重装几个系统依赖。

> 以前按旧文档用 `playwright install` / `playwright install-deps` 装过、并且以 root 运行的：浏览器当时装在容器的 `/root/.cache` 里，系统库也没有登记，重建后两样都已经丢了。升级后点一次一键安装即可，以后重建就不会再丢。

### 浏览器目录 `PLAYWRIGHT_BROWSERS_PATH`

Playwright 靠环境变量 `PLAYWRIGHT_BROWSERS_PATH` 决定到哪里找浏览器。没设的话它会用 `~/.cache/ms-playwright`，在 Docker 里就是容器的可写层，**重建即丢** —— 这正是以前重建后脚本报 `Executable doesn't exist` 的原因。

现在 **Docker 部署下面板会替你设好默认值**：数据目录下的 `deps/ms-playwright`（Docker 默认 `/app/Dumb-Panel/deps/ms-playwright`）。定时任务、调试运行、`ddp shell` / `ddp python`、依赖安装拿到的默认都是这个值。

- **你自己设了，就以你的为准。** 在面板「环境变量」页里启用了同名变量，或者在容器环境（compose 的 `environment` / `docker run -e`）里设了它，面板都不会覆盖；一键安装下载 Chromium 时也按你的值下载。两处都设了时，「环境变量」页里的优先。
- 自己设的路径记得放在数据卷里，否则重建照样丢。
- Windows 桌面版、裸机二进制、Magisk 模块不设默认值，保持 Playwright 原本的行为。
- 以前用 `PUID` 降权运行的，浏览器原本在数据目录下的 `.home/.cache/ms-playwright`（本来就在数据卷里）。升级后面板启动时会自动把它搬到新目录，不用重新下载。

### 用 `PUID` / `PGID` 降权运行时，系统库要手动装

apt 要写系统目录，必须 root。设了 `PUID` 的容器里，「安装 Playwright 运行环境」按钮（以及「新增依赖」下拉菜单里的同名入口）会置灰，旁边直接写明当前以非 root 运行、装不了系统库，也就不会建出一批失败记录。两个选择：

- **推荐：去掉 `PUID` / `PGID`，改回 root 运行**，再点一键安装。这样系统库会登记成 Linux 依赖，重建后自动重装。
- **坚持降权运行**：Python 包和浏览器照常在面板里装 —— 到「依赖管理 → Python」装 `playwright`，Docker 部署下装完会自动接着下载 Chromium。系统库则要在宿主机上用 root 身份手动装（容器名按你的实际情况替换）：

  ```bash
  docker exec -u 0 daidai-panel apt-get update
  docker exec -u 0 daidai-panel apt-get install -y --no-install-recommends \
    libasound2 libatk-bridge2.0-0 libatk1.0-0 libatspi2.0-0 libcairo2 libcups2 libdbus-1-3 \
    libdrm2 libgbm1 libglib2.0-0 libnspr4 libnss3 libpango-1.0-0 libx11-6 libxcb1 \
    libxcomposite1 libxdamage1 libxext6 libxfixes3 libxkbcommon0 libxrandr2 \
    fonts-liberation fonts-wqy-zenhei fonts-noto-color-emoji libfontconfig1 libfreetype6
  ```

  ⚠️ 这样装的系统库**没有登记**，面板不知道它们的存在，**重建容器后会丢**，每次重建都要重新执行一遍。

### 手动方式

不想用一键安装，或者只想补下载浏览器时：

```bash
# 1. Python 包：到面板的「依赖管理 → Python」里装 playwright
#    （Docker 部署下装完会自动接着下载 Chromium，通常到这一步就够了）

# 2. 需要单独补下载浏览器时，进容器用与任务完全一致的环境开一个 shell
docker exec -it daidai-panel ddp shell

# 3. 在这个 shell 里下载 Chromium（会下到 PLAYWRIGHT_BROWSERS_PATH，也就是数据卷里）
python -m playwright install chromium
```

> 用 `ddp shell` 而不是直接 `docker exec -it daidai-panel sh` —— 前者会把面板托管的 venv 前置到 `PATH`，并带上与任务一致的 `PLAYWRIGHT_BROWSERS_PATH`，`python` 才找得到 playwright，浏览器也才会下到数据卷里；后者进去的是系统环境，这两样都没有。
>
> ⚠️ **不要再用 `playwright install-deps` 装系统库。** 它直接调 apt，装下的包不会登记成 Linux 依赖，面板不知道它们的存在，**重建容器就丢**。系统库请用一键安装，或者在「依赖管理 → Linux」里逐个添加。

不想进容器的话，面板里也有命令行：**依赖管理 → 「新增依赖」旁的下拉菜单 → 系统命令行**（仅管理员）。它一次执行一段非交互命令，同样可以跑 `python -m playwright install chromium`；但它用的是面板进程自己的环境，**不带「环境变量」页里的变量** —— 如果你在那里另设了 `PLAYWRIGHT_BROWSERS_PATH`，请改用上面的 `ddp shell`。

### Alpine 版镜像跑不了浏览器，请用 Debian 版

面板默认的 Alpine 镜像是 **musl** 环境，而 Playwright 官方下载的 Chromium 是 **glibc** 构建的，**在 Alpine 里根本无法执行**。一键安装在 Alpine 版上会直接提示不支持，`playwright install-deps` 也只支持 Debian/Ubuntu。

Python 的 `playwright` 包在 Alpine 上连装都装不上：它的每个版本都只发布认 glibc 的 `manylinux` 预编译包，没有 musl 能用的包，也没有源码包。不管是在「依赖管理」里装，还是任务运行时自动安装缺失依赖，pip 都会报下面这几行（第一行是你配置的镜像源）。这不是网络问题，换源、重试都不会有变化：

```text
Looking in indexes: https://mirrors.cloud.tencent.com/pypi/simple
ERROR: Could not find a version that satisfies the requirement playwright (from versions: none)
ERROR: No matching distribution found for playwright
```

Node.js 的 `playwright` npm 包在 Alpine 上能装上，但它下载的 Chromium 同样是 glibc 构建，照样启动不了（脚本也可以用 `connect` / `connectOverCDP` 连接别处的浏览器）。`v3.3.4` 起，任务日志、失败通知、调试运行里碰上这几种情况，面板会直接提示该换什么。

要跑浏览器自动化，请改用 **Debian 版镜像**（数据卷可以直接沿用），换好之后到「依赖管理 → Linux」点「安装 Playwright 运行环境」。仓库里有现成的 `Dockerfile.debian` 和 `docker-compose.debian.yml`，镜像标签的完整对照见 [README → Alpine 与 Debian 运行时和镜像标签](../README.md#alpine-与-debian-运行时和镜像标签)。面具模块版同理：改刷 Debian 版模块（`daidai-panel-magisk-debian-vX.Y.Z.zip`），再在终端执行 `python3 -m playwright install --with-deps chromium`；安卓上能否跑起 Chromium 目前没有验证过。

### `/dev/shm` 默认只有 64MB，Chromium 会崩

容器的 `/dev/shm` 默认大小是 64MB，Chromium 很容易因此崩溃（通常表现为浏览器启动后立刻挂掉，或跑几个页面之后突然失联）。三种解法任选其一：

| 部署方式 | 怎么改 |
|----------|--------|
| `docker run` | 加 `--shm-size=1g` |
| Docker Compose | 服务下加一行 `shm_size: 1gb` |
| 不想改部署 | 给浏览器加启动参数 `--disable-dev-shm-usage` |

### 「调试运行」能跑通，不代表定时任务一定能跑

这条容易被理解反，说清楚：

- **两条链路用的是同一套环境构造**：同一个用户、同一份 `PATH`、同一个托管 venv、同一批注入的环境变量。所以调试运行能跑通，**确实**说明依赖、浏览器、系统库这些都装对了。
- **差别只在调度那一侧**：调试运行**不经过调度器**，也**不写任务日志**。定时任务多出来的那一段 —— 注册进调度器、到点触发、排队、通过多实例闸门 —— 调试运行一步都不走。

所以「调试运行没问题」这个事实，能排除环境，**排除不了调度**。碰上「调试运行好好的、定时任务没日志」，答案就在前面 6 步里，重点看[第 2 步](#2-看下次运行列旁边有没有警示图标)和[第 4 步](#4-看状态列是不是停在运行中)。

## 一页速查表

| # | 在哪里看 | 什么算正常 | 不正常怎么办 |
|---|----------|-----------|--------------|
| 1 | 「定时规则」列 | 一段 cron 表达式 | 显示「手动运行 / 开机运行」→ 编辑任务，把「定时类型」改成「常规定时」 |
| 2 | 「下次运行」列 | 有时间，且**没有橙色警示图标**（灰色信息图标不是故障） | 橙色图标提示「未注册到调度器」→ 打开任务编辑弹窗，什么都不改直接保存 |
| 3 | 「下次运行」的具体时间 | 那个时间**还没到**，就说明它本来就不该跑 | 从脚本页加的任务预填每天 00:00 → 手动点「运行」验证，或改定时规则 |
| 4 | 「状态」列 | 不跑的时候是「空闲中」 | 停在「运行中」→ 点「停止」，或设超时时间，或开「允许多实例」；任务详情里看「最近一次被跳过」 |
| 5 | 「上次结果」列 | 与日志内容一致 | 有结果但没日志 → 被保留策略清了（默认 7 天），按需调大 |
| 6 | 设置 → 面板日志 | 搜不到异常关键词 | 搜「跳过」「入队失败」「注册调度失败」，按提示的原因处理 |
