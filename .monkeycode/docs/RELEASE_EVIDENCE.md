# Release Evidence

Release evidence is generated by `go run ./scripts/generate-release-evidence.go`. The generator creates evidence structure; final release status also requires strict runtime, device, Recovery APK, upgrade/recovery, stability, and public-download records.

The single version source is `VERSION.json`. Its current values are version `1.0.13` and Android version code `1000130`; `scripts/version.py check` validates derived project versions.

## CI Flow

1. Resolve and validate `VERSION.json`.
2. Signed releases validate signing secrets and prepare the keystore. Tag builds require verified same-commit ARM64 device evidence; stable workflow dispatches accept the same-commit cloud workflow's explicit blocked ARM64 evidence and preserve it in the release bundle.
3. Prepare runtime inputs; run Go, runtime-contract script, and route-contract checks.
4. Build and inspect the mobile Core AAR; resolve Flutter packages; run Flutter and Kotlin checks.
5. Snapshots generate local smoke evidence. Stable workflow dispatches import and validate cloud blocked evidence. Tag verification adds `--strict` and requires verified ARM64 device records.
6. Build the Android ARM64 APK, extract embedded runtime metadata, compare it to repository inputs, and repeat runtime verification using the APK.
7. Generate APK SHA-256, update manifest, and `release/evidence/`; upload CI artifacts.
8. For tags, verify the signing certificate and attach the APK, SHA-256, update manifest, and evidence archive to the GitHub Release.

## Snapshot And Tag Gates

Snapshot builds may carry blocked runtime smoke evidence because their runtime verification omits `--strict`. They provide integration artifacts and do not establish device readiness.

Tag builds use repository/device evidence without regenerating snapshot smoke data. They require strict runtime verification before and after packaging, a matching tag/version, formal signing, and a successful same-commit device workflow whose three required matrix records each report eight passing runtimes. Stable workflow dispatches require formal signing and a successful same-commit device workflow, preserve explicit ARM64 blocked evidence, and disclose the cloud runner limitation in release notes.

The device workflow can emit a blocked API 35/16K record when the required emulator image is unavailable. External JSON remains unverified and blocked. Physical-device evidence requires an explicitly requested self-hosted ARM64 run. Current repository smoke records are blocked, so the real runtime/device gate remains open.

## Script Inputs

| Flag | Purpose |
|---|---|
| `--apk` | Release APK path used for SHA-256 artifact evidence. |
| `--version` | Release or snapshot version label. |
| `--output-dir` | Evidence output directory, defaulting to `release/evidence`. |
| `--runtime-manifest` | Runtime manifest input, defaulting to `runtime/manifest.json`. |
| `--runtime-smoke` | Runtime smoke evidence input, defaulting to `runtime/smoke-evidence.json`. |
| `--compatibility` | Runtime compatibility source, defaulting to `runtime/compatibility.json`. |
| `--route-trace` | Backend mobile route trace, defaulting to `contracts/backend-api-mobile.json`. |
| `--go-mod` | Go module dependency input. |
| `--flutter-lock` | Flutter dependency lock input. |
| `--package-lock` | Node dependency lock input. |
| `--git-commit` | Commit identifier recorded in the evidence manifest. |
| `--actor` | Release actor recorded in the evidence manifest. |
| `--repository` | Repository identifier recorded in the evidence manifest. |

## Generated Files

| File | Contents |
|---|---|
| `release-evidence.json` | Top-level manifest linking release metadata, APK/runtime/route artifacts, generated reports, and Task 6.3/6.4 gate status. |
| `sbom.cyclonedx.json` | CycloneDX 1.6 SBOM built from bundled runtimes plus Go, Flutter, and Node lockfiles. |
| `third-party-licenses.md` | License handoff table for SBOM components. |
| `runtime-manifest.release.json` | Runtime manifest snapshot copied into the release evidence bundle. |
| `route-trace-summary.json` | Route count, module/status matrix, test-case coverage, source commit, and fixture summary. |
| `compatibility-matrix.release.json` | API/page-size/runtime matrix rows for required device verification. |
| `page-size-report.json` | 4 KB and 16 KB page-size report placeholders per runtime entrypoint. |
| `test-report-placeholders.json` | Go, Flutter, Kotlin, and runtime test-report handoff structure. |
| `core-cycle-evidence.json` | Append-only schema for the 100 Core cycle gate. |
| `api-matrix-evidence.json` | Append-only schema for API 28, 29, 31, 34, and 35 device matrix runs. |
| `scheduler-24h-evidence.json` | Append-only schema for the 24-hour scheduling SLO run. |
| `scheduler-7d-evidence.json` | Append-only schema for the seven-day scheduling SLO run. |
| `README.md` | Human-readable index for release evidence artifacts and report names. |

## Device Evidence Records

Task 6.4 device and stability records are intentionally append-only. Real-device operators attach rows to the generated JSON files after targeted runs finish.

The 100 Core cycle record captures cycle number, API level, device, start/stop timestamps, database hashes before and after the cycle, status, and notes.

The API matrix record captures API level, device, page size, APK SHA-256, Core start result, runtime smoke result, route contract result, upgrade/recovery result, status, and notes.

The 24-hour and seven-day scheduler records capture task identity, scheduled UTC, expression hash, process start UTC, monotonic delta, API level, device, scheduling policy, status, and reason code.

## Release Gate Usage

The replacement release can be labeled final only after all generated placeholders have accepted real-device records, the public APK re-download SHA-256 matches the CI artifact, and the Modern plus Recovery APK upgrade order is verified.

Current open evidence includes production runtime assets, accepted eight-runtime device smoke, Kotlin and Flutter pass reports, the real API/page-size matrix, 100 Core cycles, 24-hour and seven-day scheduling, low-storage, Doze, restart, process-kill, public re-download, and upgrade/recovery runs. A separately built, signed, and verified Recovery APK also remains pending.
